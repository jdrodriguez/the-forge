# Plan: a new person can install The Forge and run it on one to four computers

Written 2026-11-10. This is the spec the build works from. Each piece below is built whole for its own scope: no stubs,
every acceptance check run before it merges.

## Why

The repo packages a system that runs today on one person's three computers. Its board was brought up to date on
2026-11-09. Three things still stand between the repo and someone else using it:

1. **Setup is a README of manual steps.** It assumes you already know Tailscale, SSH between machines, how several
   Claude accounts sit on one computer, and how Codex and Grok sign in.
2. **The map assumes three or more computers.** Rohan is drawn only as the leftover for "any other machine", and a
   person with one computer sees one realm.
3. **The repo's dispatcher does less than the live one.** It starts no Codex or Grok workers, and it lacks the recovery
   and backpressure the live dispatcher has gained since 2026-11-05.

The goal: `npx the-forge setup` on a clean Mac, an interview with Claude, and a running queue with the full map, on
one, two, three or four computers.

## Decisions already made by the owner

- No setup screen. A Claude Code skill interviews the user and sets things up.
- The interview asks: how many computers (1 to 4), how many Claude accounts, how many Codex and Grok accounts, which
  Claude account is the main one, which are the workers.
- One computer with one Claude account still gets the whole map. Workers go to different realms as they take work.
- Rohan is drawn as a full fourth realm now, before a fourth computer exists.
- It ships as a node package, installed and started from the terminal with one command.
- The repo should hold everything the live system does.

## Phase 1: four pieces

Each piece is one worker on its own branch, opening a pull request against `main`. A and C start first. B follows A on
the same branch. D starts from the contracts below and rebases once A, B and C are merged.

### A. Rohan is a named fourth realm

The audit (`rohan-fourth-realm.md`) found a full Edoras on the map and only a tent in the side view. Rohan cannot be
named in config, Men sit at the elves' desks, a fourth machine reuses the first machine's colour, and a merge in Rohan
plays Rivendell's harp.

Build:
- Config: `queueBoard.realms` accepts `rohan`. With no map, enabled hosts take Rivendell, the Shire, Erebor and Rohan
  in that order. `queueBoard.nicknames.rohan` is a pool of Men's names. A fifth host keeps today's fallback.
- Server: `snap.config.realms[host] = { name: 'Rohan', folk: 'man', key: 'rohan' }`. Every realm entry gains `key`.
- Page: a fourth machine colour, Rohan in the `REALMS` table, and nothing that treats Rohan as "no entry".
- Side view: Meduseld, stables and a training yard in place of the tent, a Rohan station (not the lectern), work
  rounds for Men (horses, water, sword drill), horses in a paddock, and night lights on the hall.
- Map: Edoras is the named Rohan. A Rohan station graphic. One Rohan chore at dawn or dusk (a banner or the watch).
  The spare Edoras hall is no longer drawn only when no machine is Men.
- Layout: with four realms, no realm overlaps another realm or a landmark at 1100x900, 1400x900, 1790x1260,
  2400x1500 and 390x844. Aragorn's Weathertop post no longer overlaps Rivendell.
- Sound: `merge-rohan.wav` from `sounds/make.mjs` (a horn of the Mark), `MERGE_CUE.man`, and the herald test updated.

Acceptance:
1. A four-machine snapshot fixture, kept in the repo with invented data, draws four realms in both views with workers
   at their own stations, working, at all five sizes, with no page error and no overlap (the map's own collision check
   plus a screenshot per size attached to the pull request).
2. A merge on the Rohan machine plays the Rohan cue (herald test).
3. A three-machine snapshot looks exactly as it does today (screenshots before and after at 1790x1260).
4. A page smoke test runs in `npm test` or `npm run test:page`: every view, both fixtures, no uncaught error.

### B. One computer, full map

The audit (`one-computer-mode.md`) confirms a drawing-only projection works if the rest of the page keeps the real
snapshot.

Build:
- Config: `queueBoard.spreadRealms`: `"auto"` (the default: on when exactly one host is enabled), `true` or `false`.
- Server: every live ticket carries `realm` (a realm key). Normally it is its machine's realm. With spread on, the
  server assigns the realm with the fewest live workers when the ticket starts, keeps it for the ticket's life, and
  remembers it for merged tickets. Nicknames come from the assigned realm's pool. `snap.config.spread` says it is on.
- Page: the two Middle-earth views read one derived snapshot through a single accessor. With spread off it is the real
  snapshot, so nothing changes. With spread on, each realm is a virtual machine: its own id, its share of the worker
  and Sentry slots (the totals stay the machine's own), the tickets assigned to it, and the real machine's health.
- Bridges back to the real machine, each from the audit: who called (lights, messengers, eagles), Gollum (one Gollum,
  in the first realm, opening the real machine's findings), machine health notes, merged tickets and their fireworks,
  the merge cue (by the ticket's realm), and every click that opens another view.
- The Queue, Machines, Worktrees, Sessions and Gollum views keep showing the one real machine.

Acceptance:
1. A one-machine fixture with eight live workers draws four realms with two workers each, in both views.
2. A worker keeps its realm and its name across ten snapshots while others start and finish.
3. A merge plays the cue of the realm the worker sat in.
4. Clicking a worker opens its session panel. Clicking Gollum opens the real machine's Gollum page.
5. Slot totals in the header and the Queue view equal the machine's `maxWorkers`.
6. With `spreadRealms: false`, the same fixture draws one realm, as today.
7. A three-machine fixture is unchanged by this piece (screenshots before and after).

### C. Codex and Grok as queue workers

The audit (`live-vs-repo-gap.md`, first table) lists the live files. The board already shows engine workers.

Build, in `dispatcher/`:
- `engine-workers.mjs`, the contained runner (`ext-worker.sh` with its library and network proxy), the engine worker
  brief, the engine state folders, and their tests and self-test, ported to the repo's standard. Repository-specific
  gates and instructions come from config (`push.gates`, `premerge.*`) and the brief template.
- Account choice: Claude accounts and engines ranked together by weekly usage left. Engines take only tickets of the
  configured sizes, never Sentry tickets, never tickets labelled `claude-only`.
- One slot pool per machine: Claude, Codex and Grok workers share `hosts.<name>.maxWorkers`.
- Config, with Notes: `dispatcher.externalBuilders.fallback.{enabled, engines, sizes, maxRounds, timeoutSeconds,
  limitCooldownMinutes}`. Off by default.
- What containment does and does not protect is stated in the dispatcher README, as the live one states it.

Acceptance:
1. The ported engine tests and the containment self-test pass on macOS. The Linux path is checked on a Linux machine
   or reported as not checked.
2. With engines off, the dispatcher's existing tests pass unchanged.
3. A dry run with a fake Codex binary takes a size S ticket through build, one review-fix round and hand-off, and the
   board's snapshot shows it as an engine worker in a normal slot.
4. An engine never receives a Sentry ticket or a `claude-only` ticket (tests).

### D. Setup by interview, and the package

Build:
- `bin/the-forge.mjs`, no dependencies, declared in `package.json` (`bin`, `files`, not private):
  - `setup`: installs a lasting copy (default `~/the-forge`; an npx cache is temporary and launchd must point at a
    path that stays), checks what is missing, links the skills, and starts Claude Code on the setup skill. Without
    Claude Code it prints how to install it.
  - `init --answers <file>`: writes `agent-queue.config.json` from an answers file. No questions. This is the one
    place config is generated, so it can be tested.
  - `doctor [--json]`: node, git, gh sign-in, Claude Code, each Claude account's sign-in, Codex and Grok where
    enabled, Tailscale, SSH to each other machine, the Linear key, the config against the example.
  - `install` and `uninstall`: the dispatcher, board and herald jobs on this machine (launchd or systemd).
  - `start`, `stop`, `status`, `open`, `update`.
- The answers file: computers (host, ssh address, system, which is the board's), Claude accounts (label, which is the
  main one, which are workers, which computers each is signed in on), Codex and Grok per computer, the person's name,
  the repository, Linear team, Slack (optional), the weather place (optional), realms (optional).
- One Claude account: it is both main and worker. `init` sets every machine's `accounts` to it and leaves the
  headroom floor in place.
- `skills/forge-setup/SKILL.md`: the interview (the owner's questions, one at a time), then `init`, then each
  computer in turn (Tailscale, SSH keys, the copy of the repo, `the-forge install`), then accounts, then Codex and
  Grok, then `doctor` until clean, then one test ticket. Signing in is always the person's own step: the skill names
  the exact command and waits.
- `docs/setup.md`: the same ground as a written guide, for one to four computers: what to buy or reuse, Tailscale,
  SSH, the Claude accounts and how several live on one computer, Codex, Grok, Linear, GitHub, Slack, what each
  computer runs, how to add a computer later.
- A GitHub Actions workflow that runs `npm test` on every push.
- The package is built ready to publish. Publishing is the owner's step: it makes the code public and needs an npm
  sign-in.

Acceptance:
1. `npm pack`, then install the tarball into an empty prefix: `the-forge --help` and every subcommand's `--help` work.
2. `init --answers` for 1, 2, 3 and 4 computers, and for one Claude account, each writes a config that the loader
   accepts and that `docs/configuration.md`'s keys cover (tests, one per case).
3. `doctor` in an empty home reports each missing thing by name and exits non-zero. On the owner's machine it reads
   clean, or names what it found.
4. `setup` in a throwaway home with a fake `claude` on the path installs the copy, links the skills and starts the
   skill (test).
5. `npx github:<owner>/the-forge setup --dry-run` runs from the private repo before anything is published.
6. A person who follows `docs/setup.md` on one computer with one account reaches a board with four realms. The
   reviewer walks it on a clean user account, or says it was not walked.

## Phase 2: the rest of what the live system does

One ticket each, in this order, each specified before it is built. Sources are in `live-vs-repo-gap.md`.

1. Work survives a spent account: checkpoints and hand-offs between accounts, machines and engines.
2. Reviewer parking, the Sentry cascade and the cap on parked Sentry pull requests.
3. Duplicate-build prevention and claim races between machines.
4. The combined orchestrator watcher, its stop guard, and the general inbox tools.
5. Merge-request recovery, migration ordering and stale approval stamps.
6. Slack triggers and main-watch reliability.
7. Account and model policy, reset reminders and Codex reset.
8. Fleet: sign-in refresh grace, main-checkout sync, disk cleanup, Remote Control services.
9. Sentry triage as a module configured per project.

Left out, because they are one company's own: firm intake, site tools, staging-deploy watchers tied to one app's
layout, the backup and symlink scripts. The older external-builders pilot is replaced by piece C.

## Contracts between the pieces

- Realm keys: `rivendell`, `shire`, `erebor`, `rohan`. Folk: `elf`, `hobbit`, `dwarf`, `man`.
- `snap.config.realms[host] = { key, name, folk }`. `snap.config.spread` is a boolean. `tickets[].realm` is a realm key.
- Engine settings live at `dispatcher.externalBuilders.fallback`. The board reads `machines[].engineAccounts`.
- The package's command is `the-forge`. The lasting copy defaults to `~/the-forge`. The config file keeps its name.
- Only the piece that owns a file edits it. A piece that needs something from another writes it in its pull request.
