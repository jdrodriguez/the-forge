# The dispatcher

The human starts work by adding the ready label (`agent-ready` by default) to a spec'd Linear ticket. A launchd job (macOS) or a systemd user timer (Linux) runs `dispatcher.mjs tick` every 20 minutes. Each tick hands ready tickets to fleet workers, merges their PRs when GitHub calls them clean, and moves the tickets to Verifying. Anything that needs the human goes to their inbox (`../inbox/ask-human.sh`).

A tick spends no Claude tokens. It is a plain Node script that reads Linear, GitHub and the fleet's session list, and with an empty queue it doesn't even query account usage. The tokens go to the workers, and the caps in the config bound those.

Every value below in `code` that names a setting lives in `agent-queue.config.json` (see the example at the repo root). Most are under `dispatcher`.

## Labels (the state machine, kept in Linear)

| Label (config key, default) | Meaning | Who sets it |
|---|---|---|
| `linear.labels.ready`, `agent-ready` | The ticket meets the queue bar in `../specdesk/SPECDESK.md`: the spec-floor sections, a Size label in `queueSizes`, a priority, a project, no open product question | the human, usually through the spec session |
| `linear.labels.building`, `agent-building` | Claimed, and a fleet worker is building it (the ticket also moves to In Progress) | the dispatcher |
| `linear.labels.stuck`, `agent-stuck` | The dispatcher gave up: the worker's session ended with nothing moving for `stallHours`, or the PR was closed. The human decides what happens next | the dispatcher |
| `linear.labels.needsHuman`, `needs-human` | An ask is open on the ticket | `ask-human.sh` |
| `linear.labels.mechanical`, `sentry-mechanical` | A Sentry fix whose PR the dispatcher merges once it is green (see Sentry merge paths) | your Sentry triage |
| `linear.labels.judgment`, `sentry-human-review` | A Sentry fix whose PR waits on the reviewer's GitHub approval before it merges | your Sentry triage, or the dispatcher when a mechanical fix turns out to need a human call |

After a merge, the dispatcher removes the building label and moves the ticket to Verifying. The human's verification flow takes it from there. To re-queue a stuck ticket, remove the stuck label and add the ready label.

## What a tick does

0. **Inbox upkeep.** `ask-human.sh sweep` posts any open ask that hasn't reached Slack and removes the needs-human label from answered ones.
1. **Check main.** For each commit it merged in the last day, a failed CI run on main trips the circuit breaker, unless a later main commit containing that merge passed the same workflow (a flake), waiting up to `flakeWaitMinutes` for one.
2. **Advance.** For each ticket this machine dispatched, it finds the PR by its branch (`github.branchTemplate`, `agent/{id}` by default):
   - merged: moves the ticket to Verifying;
   - closed: marks it stuck;
   - green (`mergeStateStatus` CLEAN, the `github.reviewCheck` check passed, no open review thread): squash-merges it after the pre-merge check. With a merge queue on the base branch, the merge call enqueues the PR, a queued PR is left to the queue, and the dispatcher deletes the branch once it reads merged. If the PR touches a path in `riskyPathPatterns`, it writes `merge-requests/<ID>.json` in `paths.sharedDir` for the orchestrator session instead, which reviews those paths, runs the pre-merge check and merges. Finished, green, built-to-spec work never waits on the human's merge button, since a worker waiting on a merge holds its slot. The orchestrator escalates to the human only for a trust boundary or a change beyond the ticket's spec;
   - not green yet: checks for progress instead of elapsed time. There is no time limit. Progress is a new commit on the branch, any PR activity, or the worker's session showing busy. Every `longRunNoticeHours` it posts an informational "still going" line to Slack. If nothing has moved for `stallHours` while the worker isn't busy, or the worker has been busy `spinHours` without a commit or PR change, the human gets one stall note and the ticket stays in the queue. While the ticket waits on the human's answer, it is never called stalled. Only a worker whose session is gone on two checks in a row, with nothing moving for `stallHours`, makes the ticket stuck.
3. **Watch workers.** A worker whose session shows `blocked` (waiting on input) has stopped, and the stall check would only notice hours later. The first tick that sees it puts an ask in the human's inbox with the `claude attach` command for that session. It asks once per block and logs when the worker moves again. This step runs while the dispatcher is paused, too. A fleet account that signs out gets one ask the same way.
4. **Dispatch.** A machine with no room claims nothing: over `maxLoadPerCore` on its 5-minute load average, or under `minMemoryFreePercent`, it logs why and leaves every ticket ready for its next tick or another machine's. `hosts` sets each machine's `maxWorkers` and which fleet `accounts` it may use. `maxWorkers` counts every working fleet worker on the machine: the queue's own, plus any background worker another session started outside the queue. A worker that is idle or done, or a session row with no process, takes no slot. First it checks every ready ticket against the bar's mechanical part: a `## Acceptance scenarios` section, a Size label in `queueSizes`, and a priority. A ticket that fails loses the ready label, gets a comment saying why, and lands in the human's inbox. Then, within `maxConcurrent` (counted across machines through the building label) and `maxDispatchesPerDay` when one is set, it takes ready tickets by priority, then age. It skips tickets whose "blocked by" tickets aren't done or in Verifying. It picks the account with the most weekly headroom that has a free worker slot and at least `headroomFloorPercent` left in both its 5-hour and weekly windows: a Claude fleet account, or, while the engines are on and the ticket is one an engine may take, Codex or Grok (see Codex and Grok as queue workers). Then it claims the ticket and runs `fleet.sh dispatch` with `worker-brief.md`, or starts the engine through `ext-worker.sh`.
5. **Sentry triage**, when `sentryTriage.enabled` and this is `sentryTriage.host`: starts your triage module (see below).

**Bundling:** a lead ticket takes up to `bundle.maxTickets - 1` companions into its worker, branch and PR: other ready tickets in the same Linear project that are linked to the lead or to a companion already taken (same parent ticket, or a direct blocks or related link; a shared project alone is not enough), sized in `bundle.sizes`, with no open "blocked by" outside the bundle (a companion blocked by the lead is fine). Every extra PR costs CI runs and a review round. A ticket whose description has a `Ships alone: <reason>` line, which the spec session writes on a ticket it sliced thin on purpose, never bundles. The worker gets one brief with a bundle note and every ticket's section, gives each ticket its own commits, and titles the PR with every ID. The lead's state entry carries `bundle`; each companion's carries `bundledInto` and the status `bundled`, which nothing advances on its own: it moves to Verifying when the lead merges, to stuck when the lead goes stuck, and out of the queue when the lead's PR is closed under review. A question about a companion counts as the lead waiting. Each machine lists its live bundles in `paths.sharedDir/bundles/`, so `maxConcurrent` counts a bundle as one worker. `tick --dry-run --bundle` shows what bundling would do while it is off. Tests: `test/dispatcher-bundle.test.mjs`.

**Sentry slot:** a host with `hosts.<name>.sentryWorkers` keeps that many side worker slots for Sentry fix tickets, the ones labeled `linear.labels.sentry`. They sit apart from its `maxWorkers`: a Sentry ticket never takes a regular slot there, a regular ticket never takes a Sentry slot, and the slot sits idle when there is no Sentry work. Every machine writes `heartbeats/<host>.json` in `paths.sharedDir` each tick. While a Sentry host's heartbeat is under `sentryHeartbeatMinutes` old and unpaused, the other machines leave Sentry tickets to it ("left for <host>'s Sentry slot"); when it is offline or paused, they build Sentry tickets as usual, so a fix never waits on one machine. Bundles never mix Sentry and regular tickets. Tests: `test/dispatcher-sentry.test.mjs`.

**Sentry merge paths:** your Sentry triage gives each fix ticket a merge path: a label and a `## Merge path` section with the reason on a `Reason:` line. **Mechanical** needs all of these: the diagnosis pins the cause to a file and line with high confidence; the fix is Size S in one package; it needs no migration; none of its files match `riskyPathPatterns`; it needs no product or behavior choice; and a regression test can prove it. **Judgment** is everything else, including any fact the diagnosis left out.

- A mechanical PR merges when green, like any queue PR. If it turns out to touch a reviewed path, it goes to the reviewer instead of the orchestrator. The same happens when its worker writes `Merge path: human-review: <reason>` in the PR body (`worker-brief.md`), since workers can't write to Linear. In both cases the dispatcher swaps the label.
- For a judgment PR that is open and not a draft, the dispatcher does three things once each, recorded in `state.json` under the ticket's `reviewer` entry: it requests `reviewer.github` as reviewer (`gh pr edit --add-reviewer`), comments the PR link and the reason on the ticket, and DMs `reviewer.slackUser` through the queue's Slack bot.
- The DM goes to the reviewer's user ID with `chat.postMessage`. With `chat:write`, a `U…` ID as `channel` posts to the user's DM with the app (its App Home Messages tab). If the app's Messages tab is off, Slack answers `messages_tab_disabled`, and the dispatcher falls back to `reviewer.fallbackChannel` with a mention. Slack timeouts are never retried, so the reviewer never gets two messages.
- A judgment PR merges only when the reviewer's latest review approves the current head and the PR is green. Without branch protection, GitHub's `reviewDecision` stays empty and a review bot may post APPROVED reviews of its own, so the gate reads the reviewer's reviews by login. When commits land after their last review, they are asked again once for the new head.
- While it waits, the note reads "waiting on <reviewer>'s review", and it is never counted as stalled.
- When their latest review requests changes on the current head and the ticket's worker has ended, one replacement worker starts on the same branch. Its brief quotes the review and inline comments, and tells it to push once and reply on each thread. A worker that is still live is left to handle it. Each review gets at most one worker, and a review round does not use up `maxRedispatches`.
- A Sentry ticket with neither label counts as judgment.

Tests: `test/dispatcher-reviewer.test.mjs`.

**Sentry triage module:** this repo ships no triage. If you write one, put it next to `dispatcher.mjs` (or point `sentryTriage.module` at it). It exports `kickFromTick({ cfg, dry, log })`, which should start its run in its own detached process so the tick never waits on it, and `statusLine(cfg)`, which `status` prints. It is loaded lazily, so a throw or a syntax error in it is one line in `dispatcher.log` and never stops a tick. Tests: `test/dispatcher-hook.test.mjs`.

**Circuit breaker:** `stuckInARowTrips` stuck tickets in a row, or a real failure on main after a merge, pauses the dispatcher (no dispatches, no merges) and puts the reason in the human's inbox.

**Red main responder:** `main-watch.mjs` runs every 3 minutes on one machine (`./install.sh --main-watch`). It reads the base branch's CI on GitHub. When main turns red, it posts to Slack (the progress webhook) with the failing jobs and first error, shows a macOS notification, writes `main-state.json` in `paths.sharedDir`, and starts an emergency fleet worker beyond the worker cap (`mainWatch.accounts`, `mainWatch.maxWorkers`). That worker is briefed to tell flake from real, then fix forward or revert, merge its own fix unless it touches reviewed paths, and report to the orchestrator. While `main-state.json` says red (and is under 15 minutes old), every dispatcher holds queue merges. If main stays red, it alerts again every `mainWatch.realertMinutes`, and starts a second responder if the first one ended (up to `mainWatch.maxResponders`). When main turns green, it posts the all-clear. The orchestrator session runs `../inbox/main-red-watch.sh` so it is woken on red and on recovery. Log: `paths.stateDir/main-watch.log`.

**Pre-merge check:** before it merges a green PR, the dispatcher checks it against the main it will land on (`premerge-check.mjs`). A PR's CI only tested it against the main of its last push, and two PRs that were each green can break main together. When main has moved since that CI run, it merges current main into the PR in a reused scratch worktree (`<repoPath>/<worktreesDir>/premerge-check`), refuses a migration prefix that two PRs both took (`premerge.migrations`), lints changed workflows with actionlint when it is installed, then runs `premerge.checkCommand`. A pass merges. A real error (output matching `premerge.errorPattern`) doesn't: the PR branch is updated with main, so its CI re-runs and shows the clash to the worker, and the ticket gets a comment. A check that couldn't finish (the compile was killed, or no CI run was found) holds the merge for a tick. This costs local CPU only, no CI run. For a hand merge, run `node premerge-check.mjs <pr>` first, or use `../inbox/merge-approved.sh`.

**Dead sessions:** a worker the fleet reports as `failed` (its session died, as every worker does when a machine reboots) gets one replacement worker after two ticks, told to continue from the old worktree and PR. Only after that (`maxRedispatches`, default 1) can the ticket go stuck. A worker that ends as `done` or disappears goes straight to the stuck rule.

**Pushing:** workers push through `gated-push.mjs`, which runs `push.gates` (format and type checks, typically) and then `git push` with `push.env`. Tests gate in CI; the hook's slow test step is what this replaces.

## Codex and Grok as queue workers

Codex and Grok can build queue tickets as full workers, beside the Claude accounts, so a queue keeps moving on whichever subscription has usage left. They are off by default: `dispatcher.externalBuilders.fallback.enabled` turns them on for every machine, and every setting is under that key (`docs/configuration.md`, with a Note per key in the example config). The logic is in `engine-workers.mjs`, `engine-rounds.mjs` and `engine-round-note.mjs`, which the tick loads only while the engines are on or a ticket is engine-driven, inside a try/catch, so a throw there costs one log line. `engine-hooks.mjs` holds the dispatcher's side.

- **One pool.** `hosts.<name>.maxWorkers` is the machine's whole build pool. A ticket still building holds one slot whoever runs it, Claude, Codex or Grok. A ticket waiting on the orchestrator's merge holds none. The Sentry slots stay apart, and a Sentry ticket never goes to an engine. Engine tickets carry the building label, so `maxConcurrent` counts them across machines like any other.
- **Which account.** For each ticket it starts, the dispatcher ranks every Claude account with room together with every engine that can take the ticket, and the one with the most weekly usage left wins (`pickAccount`). An engine can take a ticket when it is in `fallback.engines`, `ext-worker.sh available` passes it on this machine, it has not stopped on its plan limit here within `limitCooldownMinutes`, and its plan has `headroomFloorPercent` left. Plan usage comes from the board's own reader, `queue-board/ext-usage.mjs`, once a tick; neither call runs a model. An engine whose usage can't be read ranks after every account with a reading. On an exact tie an engine goes first, Grok then Codex. `fallbackAccounts` still wait until nothing else can take the ticket. An engine that fails to start is not offered again that tick, and the ticket goes at once to the next account with room.
- **Which tickets.** A ticket may go to an engine when its Size is in `fallback.sizes`, it is not a Sentry fix, it does not carry `fallback.claudeOnlyLabel` (`claude-only`), no engine on it ever tripped the containment, and its title and description hold no email address, phone number, SSN or `fallback.withholdPatterns` match, since the ticket text goes to a third-party model. Any other ticket goes to the best Claude account, or waits with one log line naming the reason. The line names the kind of data and leaves the data out. An engine ticket is never bundled.
- **Claim and record.** The claim is a Claude worker's: journaled first, then the labels and the In Progress state, and an interrupted claim is adopted from the engine's registry row or undone. The state entry carries `driver: 'engine'`, `engine`, `account` (the engine), `workerId`, `workerName`, `round` and `engineStatus`. The queue board reads exactly these (`queue-board/engine-workers.mjs`).
- **Rounds.** One spawn is one round, with a brief from `engine-worker-brief.md` (or `fallback.brief`) written to `<stateDir>/engine-briefs/`. The brief gets the same config placeholders a Claude worker's does, plus `{{GATES}}` (`push.gates`, then `premerge.checkCommand`). Round 1 builds, pushes and opens the PR. When a round ends `done` and the PR is not green for a reason a push can fix, the next round starts on the same clone with a note built from GitHub: each failing check with the last 80 lines of its failed log, each unresolved review thread, a conflict with the base branch, a draft, or no PR at all. Checks still running start nothing, and neither does a paused queue. A review check that only waits for a re-review request gets `github.rerunLabel` instead of a round. A busy engine worker is never called stalled; its time box (`timeoutSeconds`) ends it. A ticket that needs a round past `maxRounds` goes stuck; `redispatch` then hands it to a Claude worker.
- **Questions.** An engine that stops blocked has its question relayed once through `ask-human.sh`, saying the answer goes to a third-party model. Once it is answered, the next round carries the question and the answer.
- **Limits.** An engine that stops on its plan or rate limit sits out account choice on this machine for `limitCooldownMinutes`, and hands the round to the other engine when it can run here, keeping the round number. Otherwise the ticket goes back to the queue: the engine's committed work is pushed from its clone with every hook off, the ready label goes back on before the building label comes off, and the branch is kept for the next worker.
- **Containment stop.** A `failed` run whose report starts `containment:` means the after-run audit caught the engine doing something it must not. The dispatcher stops the run, marks the ticket stuck, never starts another round on it, writes `engine-contained/<ID>.json` in `paths.sharedDir` so no machine's engine takes it again, and asks the human with the report and where the run's files are. Any other failure (a timeout, an install error, a crash) gets one retry round, then the ticket goes stuck.
- **Merge: the orchestrator only.** An engine-driven PR never merges through the dispatcher, whatever paths it touches. Once green, and once its round has ended, it goes to the orchestrator like a risky-path PR: `merge-asked`, and `merge-requests/<ID>.json` with `driver`, `engine` and `review: "built and driven by <engine>, no Claude review yet"`. A PR an engine built and a Claude worker finished goes the same way. An engine PR that shows merged without ever being sent there gets an ALERT log line, a stop of its run and an ask: the engine most likely merged it itself. These rules live in `dispatcher.mjs` and `engine-hooks.mjs`, so they hold even when the engine modules fail to load.
- **Back to Claude.** `redispatch` gives an engine ticket to a Claude worker. It refuses while the engine's run is busy. The Claude worker is told never to run anything in the engine's clone: it cuts its own worktree from `origin/<branch>` and treats the branch as unreviewed code. The ticket drops its engine fields; `engineHistory` keeps who built it and for how many rounds.

### The lockdown: ext-worker.sh

`ext-worker.sh` is the only way an engine runs. It gives each ticket its own clone of `repoPath` at `<repoPath>/<worktreesDir>/<branch basename>`, which borrows the main checkout's objects read-only, installs dependencies with `premerge.installCommand`, and runs the CLI under one sandbox around its whole process tree: `sandbox-exec` (Seatbelt) on macOS, bubblewrap on Linux. Neither CLI's own sandbox is used. A profile that can't be applied starts nothing. The supervisor writes the registry row, `<stateDir>/engine-workers/<ID>.json`, and keeps each round's brief, event stream, audit and logs in `<stateDir>/engine-workers/<ID>/<spawn id>/`. The header of `ext-worker.sh` has the full detail.

What it protects:

- **Files.** The engine reads only its clone, the main checkout's `.git`, the toolchain, the package caches and its own run folder. Your home folder is closed: other repos, the main checkout's working files (its real `.env`), `~/.ssh`, `~/.aws`, `~/.config`, `~/.claude*`, the queue's own state folder and checkout, `~/Library`, and the real `~/.codex` and `~/.grok`. It writes only its clone and its run's temp folder, never the clone's git hooks, git config, alternates or hook folder. Each time `ext-worker.sh` itself sets the clone up it records a baseline outside the sandbox (`<stateDir>/engine-clones/`): a checksum of the clone's git config, hooks, info, alternates and hook folder. Before the dependency install, after it, and after the run, the supervisor checks that `.git` is still a real folder with no `commondir` or `gitdir` pointing elsewhere and that the baseline still holds, and runs no git command on a clone that fails; the next round's start runs none either. A `.git` anywhere below the clone's root (a nested repository, which git would enter with a config the engine wrote) fails the same check, and the supervisor's git never enters submodules. Those git commands also run with `core.fsmonitor` and hooks turned off. A changed clone stops the ticket as a containment report. Those git commands also run without your global and system git config, so an attribute the engine wrote can't pick a filter defined there. Files the engine wrote that the supervisor reads out (its question, its final reply) are read only as plain files with one link: a link to a file the sandbox kept from the engine stops the ticket instead.
- **Network.** The engine reaches only this run's proxy (`ext-worker-net.mjs`, outside the sandbox) and the loopback ports in `fallback.loopbackPorts`. Unix sockets outside are closed too (Docker's, a database's, the system bus): macOS refuses every Unix socket but the system resolver's and the system log's, and Linux mounts an empty `/run`. The proxy connects only to GitHub, `registry.npmjs.org`, the CLI's own API hosts and `fallback.extraHosts`, on ports 443 and 80, and logs every decision.
- **The rest of the machine.** macOS refuses the keychain, the pasteboard, LaunchServices, AppleEvents, launchd jobs, signals to processes outside, and the user's other terminal sessions (a pty the engine opens itself still works). Linux gets its own PID namespace and empty `/tmp`, `/run` and `/dev/shm`, which hides the session and system buses and the keyring. When the engine exits, everything left in its process group is killed, so nothing it started keeps changing the clone after the audit.
- **The environment** is empty but for what a build needs: a scratch HOME, the caches, git identity, the GitHub token and `fallback.env` (names that look like credentials are dropped). No API keys, no SSH agent.
- **The command guard** reads past gh's flags and their values (`gh --repo o/r workflow run`) and refuses secrets managers, `gh pr merge`, `gh workflow run`, `gh release`, `gh secret`, `gh auth token`, `gh api` writes to merges, dispatches, workflows, refs or settings, pushes to the base branch, force pushes and `--no-verify`.
- **The audit** reads the CLI's own event stream after the run and fails it on any attempt at the above, on any GitHub API call that names a PR's merge endpoint or a ref of the base branch (`github.baseBranch`, main or master), whatever the method, since an engine has no need for either and a read of one is treated as an attempt, on a write outside the clone, on a branch that touches CI workflows, git hooks or agent settings, and on a change to the clone's hooks or git config. The brief is scanned for secret-shaped values before anything starts.

What it does not protect, and is not closed here:

- **The CLI's sign-in stays readable.** The CLI needs its auth file, and with one sandbox layer the engine's shell can read the run's copy too. It can only send it to an allowed host, GitHub included. The audit fails a run whose commands name that file; an obfuscated read passes.
- **The CLI's refreshed sign-in comes back from the sandbox.** A CLI that refreshes its tokens during a round may rotate them, so after a round that ended clean the supervisor copies the token fields of the run's copy back into your real `~/.codex` or `~/.grok` auth file, when the copy names the same account and is newer. The copy is writable inside, and the account check is the copy's own claim, so an engine that passes the audit could put tokens of its choosing into that file. A failed or contained round copies nothing back.
- **The GitHub token is the gate.** The engine gets `fallback.ghTokenFile` when it exists, otherwise your own `gh auth token`. With a personal token that has admin rights an engine can merge, push the base branch, start workflows, or push a workflow that reads the repository's secrets; the command guard and the audit are the only checks between the engine and those. Put a token that can push branches and open PRs, and nothing more, in `ghTokenFile`.
- **The command guard can be bypassed.** It is a folder of shims first on PATH. `/usr/bin/git` or a full path to `gh` skips it.
- **The audit runs after the fact.** It reads command lines and tool inputs as text, after the run, so it catches attempts it can read, and by then a push may already be on GitHub. A command built from pieces, encoded, or written to a script and run passes it. Reading text also cuts the other way: a quoted search pattern that looks like a command (`grep "security find-generic-password"`) fails the run like the command would.
- **A process can outlive the round on macOS.** The kill reaches the engine's process group. A process that starts its own session (`setsid`) leaves the group, and macOS has no way to find it by sandbox. It is still inside the sandbox, and the next round's start refuses a clone whose `.git` was changed. Linux ends the whole PID namespace with the engine.
- **Linux can't protect a path that does not exist yet.** bubblewrap mounts only existing paths read-only, so an engine on Linux can create `.git/commondir` or move `.git`, in its run or in an install script it added for the next round. The supervisor's clone check catches it before any git command runs on the clone.
- **A repo that needs its submodules checked out can't use the engines.** A `.git` below the clone's root ends the round as a containment stop, and a checked-out submodule has one. The clone is made without submodules, so this bites only when the install command or the build initialises them.
- **GitHub is reachable by design,** so a push, a gist or a comment can carry data out.
- **DNS on macOS** still leaves the sandbox through the system resolver, so a hostname can carry data. Linux has no resolver inside.
- **Engine-written code runs elsewhere later:** in CI on its push, and wherever the branch's code runs outside a sandbox. That is why an engine PR always goes to the orchestrator for review.

**Linux.** The sandbox needs bubblewrap (`bwrap`). Ubuntu 24.04 and later stop unprivileged user namespaces through AppArmor, so bwrap fails until an AppArmor profile grants it `userns` (a file in `/etc/apparmor.d/` naming `/usr/bin/bwrap` with `userns,`, then `sudo apparmor_parser -r` on it). `ext-worker.sh available` refuses an engine while bwrap can't start, so a machine takes engine work as soon as it can.

**Proving it.** `ext-worker.sh selftest [codex|grok] [--no-model]` runs every escape as a plain command inside the exact sandbox an engine gets and reads the result from the disk, checks the audit against recorded streams of each escape, then asks the real CLI to try them. Run it after any Codex or Grok upgrade, on each machine that runs engines. It needs bash 3.2 or later and leaves canaries in the credential folders that exist under your home only while it runs.

## Staying in the loop

- **Notifications.** Every transition shows a macOS notification titled "Agent queue": started, PR opened, merged, sent for merge review, worker blocked, stuck, paused. Set `dispatcher.notify` to false to turn them off.
- **Slack.** One private channel gets two feeds, both from one Slack app.
  - Progress (started, PR opened, merged) comes from the dispatcher through the app's incoming webhook, whose URL lives in `slack.webhookFile`. `dispatcher.mjs test-notify` checks it.
  - Questions come from `ask-human.sh`. It posts each ask with the app's bot token (`slack.botTokenFile`) and links that Slack thread to the ticket as a Linear synced thread. The human answers by replying in the thread. Linear copies the reply onto the ticket as a comment, `ask-human.sh check` reads it as the answer, and the next tick's sweep removes the needs-human label. On a machine without the token, another machine's sweep posts the ask within 20 minutes.
  - Synced threads in a private channel need Linear's Slack app in the channel, as well as your own app.
- **Waiting on an answer.** A worker that asks runs `ask-human.sh wait ENG-123` as the whole Bash command with `run_in_background` and keeps building whatever the question doesn't block. An `&`, subshell or redirect detaches the wait and the worker is never woken, so `ask` prints the exact command on stderr. The wait checks every 5 minutes and wakes the worker with the answer.
- **Session start.** `dispatcher.mjs summary` prints a `[Queue]` block: what is running, each ticket's PR and why it isn't green yet, and anything merged or stuck in the last day. It reads local state only, so it costs nothing and never waits on the network. Wire it into a SessionStart hook.
- **Linear.** A saved view listing the ready, building and stuck labels shows the queue. Each ticket gets a dispatcher comment when it starts and when it merges.
- **Watching a worker.** `dispatcher.mjs status` gives each ticket's account and worker ID. Open the session with `CLAUDE_CONFIG_DIR=~/.claude-<label> claude attach <id>` (account a: `env -u CLAUDE_CONFIG_DIR claude attach <id>`).

## Commands

```
node dispatcher.mjs status
node dispatcher.mjs summary            # the session-start block, local state only
node dispatcher.mjs check ENG-123      # would the queue take this ticket? changes nothing
node dispatcher.mjs redispatch ENG-123 # new worker for a building or stuck ticket whose worker ended; continues from its worktree and PR
node dispatcher.mjs test-notify        # one macOS notification and one Slack post
node dispatcher.mjs tick --dry-run     # shows what it would do, changes nothing
node dispatcher.mjs pause "reason"
node dispatcher.mjs resume             # also resets the stuck streak
./install.sh [--main-watch] [--remove] # the scheduled jobs
node main-watch.mjs --dry-run          # what the red-main watcher would do now
node premerge-check.mjs <pr>           # the pre-merge check, by hand
./ext-worker.sh available codex        # can Codex run as a queue worker here? (cached 10 minutes)
./ext-worker.sh selftest [codex|grok]  # the containment proof, after any CLI upgrade
./ext-worker.sh stop ENG-123           # stop an engine's round by its PID
```

## Files

- **In the repo:** `dispatcher.mjs`, `premerge-check.mjs`, `main-watch.mjs`, `gated-push.mjs`, `worker-brief.md` (the template every worker gets; `{{...}}` placeholders are filled from the config and the ticket), `install.sh`. For the engines: `engine-hooks.mjs`, `engine-workers.mjs`, `engine-rounds.mjs`, `engine-round-note.mjs`, `engine-worker-brief.md`, and the lockdown, `ext-worker.sh` with `ext-worker-sandbox.sh`, `ext-worker-clone.sh`, `ext-worker-guard.sh`, `ext-worker-supervise.sh`, `ext-worker-lib.mjs`, `ext-worker-checks.mjs`, `ext-worker-audit.mjs`, `ext-worker-net.mjs`, `ext-worker-selftest.sh` and `ext-worker-selftest-probes.sh`.
- **Per machine (`paths.stateDir`):** `state.json` (this machine's in-flight tickets), `dispatcher.log`, `main-watch.log`, `PAUSED`, the secret files, and for engine workers `engine-workers/` (the registry and each round's files), `engine-briefs/` and `engine-clones/` (each clone's baseline). The engine's caches and run folders live in `~/.cache/agent-queue-ext-worker` (`EXT_WORKER_ROOT`).
- **Shared (`paths.sharedDir`):** `merge-requests/`, `heartbeats/`, `bundles/`, `main-state.json`, `engine-contained/`, `engine-built/` (every ticket an engine worked on, and the PR it opened). Keep it in a folder Syncthing or Dropbox syncs when several machines run the queue.

## Limits in this version

- Only hosts in `enabledHosts` run ticks. The claim goes through Linear labels and re-reads them just before claiming, but two machines ticking at the same moment could still both claim one ticket. Their jobs load at different times, which staggers them.
- The circuit breaker and the daily dispatch count are per machine, because the state file is.
- Tickets are watched only by the machine that dispatched them, because the state file is per machine.
- Worktree teardown after a merge is left to you.
- When a ticket gets stuck, its worker may still be running. Stop it with `fleet.sh stop` if needed.

## Tests

```
node --test test/*.test.mjs          # part of npm test
npm run test:engines                 # from the repo root: the sandboxed tests, about two minutes
```

Every test runs the real `dispatcher.mjs` in a throwaway HOME (`test/sandbox.mjs`) with stub `fleet.sh`, `gh` and `ask-human.sh`, and a stub Linear and Slack behind `fetch`. Nothing real is read or written. `DISPATCHER_SRC=/path/to/other/dispatcher.mjs` points the tests at another copy, to prove an edit before it goes live. The engine cases (`test/engine-*.test.mjs`) add a stub `ext-worker.sh` and a stub plan-usage reader. `test/sandboxed/` runs the real `ext-worker.sh` and its sandbox against fake `codex` and `grok` binaries (`test/engine-fixture.mjs`) and needs `sandbox-exec` or a working `bwrap`: the runner's refusals, rounds, questions, containment stops and stop by PID; the containment selftest; and one ticket taken end to end through its build, a review-fix round and the hand-off to the orchestrator, with the queue board's snapshot showing it as an engine worker in a regular slot. No test runs a real CLI or uses a real token.
