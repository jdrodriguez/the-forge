# Fleet levers

The levers in the board's Fleet view change the queue from the page: each machine's slots, pause and accounts, the accounts' burn, Fable and caps, the model, and the fleet-wide settings. `README.md` ("Fleet") describes what the view shows. This page says how a change behaves. The server is `control.mjs`, `control-config.mjs`, `control-ops.mjs`, `control-ops-fleet.mjs`, `control-log.mjs`, `control-state.mjs` and `control-runner.mjs`. Restart the board with `queue-board/install.sh` after editing them.

- **Small moves apply at once.** A stepper waits 0.9 seconds after the last click and sends one change. A toast offers **Undo** and **Ends...**, which adds an end time afterwards. Big moves (wind down, pause, hold new work, an account taken out, a burn or Fable turned on, Fable for the whole queue, push through) open a confirmation that says what will happen and when, with an optional end time (1, 3 or 8 hours, 11 PM tonight, 9 AM tomorrow, or a time you pick) and a reason that goes into the note.
- **Which machines a change reaches.** The levers write the config file the board reads (`AGENT_QUEUE_CONFIG`, or `agent-queue.config.json` at the repo root). A machine's dispatcher acts on a change at its next tick, once it reads that file. To reach every machine, keep one config for all of them: put it in the shared folder and point `AGENT_QUEUE_CONFIG` at it on each machine, or link `agent-queue.config.json` to it. A write follows the link, so the link stays. With a config per machine, a change reaches the board's machine only. A pause and a push through act on the named machine either way.
- **The write path.** The page never sends config. It posts one named operation, or a batch of up to six, to `POST /api/control` (`control.mjs`). The board checks the Host header first (`host-ok.mjs`) and refuses every POST on a dry-run board. `control.mjs` then wants an `X-Board: control` header and a JSON body. The server holds the allowlist (`control-ops.mjs` for machines and accounts, `control-ops-fleet.mjs` for the fleet-wide settings) and checks every field: a machine in `dispatcher.enabledHosts`, an account letter the config or a machine knows (and, to put it on a machine's list, one that machine has a folder for), a whole number in each setting's range, a known model, effort, size or engine, an end time from a minute to 14 days ahead, and a reason of at most 140 characters with no email address. Anything else is refused and nothing is written. The page sends the value it showed as `expect`, so a value that moved meanwhile is refused and shown again.
- **The file.** `control-config.mjs` reads the config, changes its `dispatcher` section, checks the file still holds what it read (its SHA-256), writes a temp file beside it and renames it over the original. A file another session or a sync tool changed in between is never overwritten: the change is refused with "try again". The layout stays the file's own: two-space JSON, keys in their order, and a new key placed after the one it belongs with.
- **The record.** Every change appends a dated line to the matching `*Note` field in the dispatcher section ("2026-11-19 ~22:10Z, Alex via the board: maxWorkers 6 to 0 (reboot); was 6, back to 6 at 2026-11-19 ~23:10Z unless changed before.") and a JSON line to the change log (`queueBoard.controlLog`, by default `control-log.jsonl` in `paths.sharedDir`). Accounts go by letter in both. `GET /api/control` sends no note field and masks any email address in what it does send. A pause and a push through change no config, so they go into the log only.
- **End times** run in the board on `queueBoard.host` only, so one process writes the file. The board checks every 30 seconds and, when it starts, catches up on any end time it missed while it was down. It puts the old value back only while the value is still what the change set. A value changed some other way since is left as it is, and the log says so. A later change on the same value takes the end time over, so a window still ends where it was going to. A burn's end time also goes into `burnUntil`, so the dispatcher stops that burn on time even while the board is down. The pending end times are what the change log says. Nothing else stores them.

## Trying the levers safely

Never point a second board at your real config: its end-time timer writes the file it reads. Copy the config into a scratch folder, set `paths.stateDir` and `paths.sharedDir` in the copy to scratch folders too, and start the board on a spare port:

```
QUEUE_BOARD_DRY=1 QUEUE_BOARD_PORT=8789 AGENT_QUEUE_CONFIG=/tmp/forge-try/config.json node queue-board/board.mjs
```

With `QUEUE_BOARD_DRY=1` every lever draws and every click gets a "dry-run board" toast while nothing is sent. Drop it to let changes land in the copy and its change log, and add `QUEUE_BOARD_CONTROL_RECORD=/tmp/forge-try/calls.jsonl` so Pause and Resume append a line to that file instead of running on a machine.

## Tests

`node --test queue-board/control.test.mjs queue-board/control-timers.test.mjs` runs the server against a temp copy of `agent-queue.config.example.json` (`control-box.mjs`): what it accepts and refuses, how it writes the file and its notes, the accounts, the HTTP route, end times, undo, the wake queue and the pause runner. A stub takes the pause calls, so nothing reaches a machine.
