# The Forge

The Forge is the queue board: a web page that shows what the agent queue is doing on every queue machine. It shows the worker slots (regular and Sentry), each ticket's machine, account, worker state, PR, CI and review state, how long it has run and when it last moved, what needs you, the ready queue, and what merged in the last 48 hours. Everything in it is drawn as Middle-earth, and a herald plays alert cues and posts notifications so you hear about a blocked worker while you work in something else.

The page has six views in its sidebar, in this order: **Queue** (what needs you, the workers, the ready queue and recent merges), **Sessions** (your Claude app sessions outside the queue), **Inbox** (your unread Linear notifications), **Middle Earth** (the same workers as animated pixel art, with **Side view** and **Top view** under it), **Fleet** (each machine's slots, health and accounts, then every account's usage) and **Worktrees** (every machine's git worktrees and their state). `#queue`, `#sessions`, `#inbox`, `#scene`, `#map`, `#fleet` and `#worktrees` open those views directly. `#fleet/<host>` scrolls to one machine's card, and `#worktrees/<host>` shows one machine's worktrees. Old links still work: `#machines` and `#control` (with or without a host) open Fleet, `#gollum` and `#gollum/<host>` open the forgotten worktrees, and `#both` opens the Top view. A bare view name opens at the top of the view. `atViewTop` in `page.html` keeps the browser from scrolling the view's first rows under the header.

**The look.** The whole board wears a Middle-earth motif. By day it is parchment and iron-gall ink with a faint paper grain. In dark mode it is Rivendell at night, deep slate with moonlit text and a few stars. Cinzel sets the headings, nav sections and worker names, EB Garamond the titles and messages, and Inter stays for chips, counts and dates so numbers read cleanly. Status marks are cut gems (hollow for not started, half-set while running, whole when done or broken), the inbox is a scroll, the queue a banner and the machines a tower. Each machine shows as its realm, in the nav, the slot groups, the machine cards and the worktree groups, with the machine's own name beside it. Every worker's slot, card and session panel shows its pixel figure from the Middle-earth view (`figureAvatar` and `paintAvatars` in `page.html`, drawn by `sprites.js`). When main is red, an "Orcs at the gates" banner sits over every view with how long, the red commit, the failing jobs and the run, and the herald sounds the war horn (see Sound).

**Realms.** A machine is drawn as one of four realms: Rivendell (elves, teal), the Shire (hobbits, green), Erebor (dwarves, bronze) and Rohan (Men, gold). The realms come from the config key `queueBoard.realms`, a map from host name to `"rivendell"`, `"shire"` or `"erebor"`. With no map, the first three enabled hosts (`dispatcher.enabledHosts`) get Rivendell, the Shire and Erebor in that order. Any further host, and any host with no entry, is a machine of Rohan. The server sends the table to the page in `snap.config.realms`, so the page names no machine.

**More marks.** Each realm has a sigil wherever a machine is named, in the nav, the slot groups, the merged rows, the session chips and the worktree groups: a leaf for Rivendell, a round door for the Shire, a gated mountain for Erebor, a pennant for Rohan and a seeing-stone for Codex and Grok (`sigil()` in `page.html`, drawn as CSS masks on `.mdot[data-r]`). Every count of what waits on you sits in a red wax seal (the sidebar's Inbox, Sessions and Needs you counts, the header's "need you", amber there when it is only worth a look, and the Needs you, Waiting on you and mentions headings), and those rows carry a seal mark, so they share no glyph with Linear's urgent priority. The main panel has a gold diamond at each corner like a map's border, each group heading runs into a double rule from a small gold diamond, and an empty state keeps its plain sentence first, then a short line in the realm's voice ("Nothing needs you right now. All is quiet in the realms."), with a gold leaf before it.

**Laid out for a human glance.** Each view reads the way a person scans it, and the page keeps to a calm core (`forge-core.css`).

- **The sidebar** (`renderNav` in `page.html`, `side-dock.js`). Only three counts wear a red wax seal, the ones you act on: Queue (Needs you), Sessions (waiting on you) and Inbox (aimed at you). Fleet carries the one worker count ("15/17"), amber when it is over. At the sidebar's foot, in plain sight: how old the data is (red once the board can't be reached or the snapshot is over 3 minutes old), the Sentry slots, then the music player and the sound buttons. Play starts and pauses the mix, and while it plays it shows pause and **Next** skips ahead. The horn mutes every alert on one click and unmutes on the next. It is struck through and red while muted, and amber while a Zoom meeting mutes it. The settings button opens its panel beside the sidebar. Play and the horn are their icons alone. The buttons stay on one row, and the playing track, its album and how far it has got take their own line under them. On a phone the same controls, Next track included, sit in the More sheet.
- **The Queue** (`queue-view.js`) is one page. **Needs you** sits at the top in the same place every time, one line per item, newest blocker first. The signed-out accounts fold into one row. A row that carries a question (an open ask, or a worker blocked on input) opens in place with the question and its recommendation. Every other row lands on what it names: a worker's session panel, a machine's Fleet card, a PR or the Linear issue. A worker waiting on you shows only here. **Workers** is one grid grouped by machine under the one worker count, with each machine's own count in its heading. **Ready** and **Merged** are one line each until opened.
- **One worker count** (`worker-count.js`, `forgeSlots(snapshot)`) is the same in the sidebar, the Queue and Fleet: slots in use over capacity. In use is every holder of a regular slot as the dispatcher counts them: a queue worker that builds, and a worker outside the queue that takes a slot. A worker whose green PR waits on a merge, or that is parked on the reviewer's review, holds none. Sentry workers sit in their own side slots and count in neither number, except on a machine with no Sentry slots. Capacity is each machine's `maxWorkers` plus its burst slots while they are open (`burstOpen`, the dispatcher's own rule).
- **The map's key** sits behind a "?" in the corner of each map (`side-dock.js`). It opens on a click, a tap or focus, and shows nowhere else.

Open the board at `http://127.0.0.1:<port>` on the machine that runs it (the port is `queueBoard.port`, 8787 by default). Add `"tailscale"` to `queueBoard.bind` and any device on your tailnet can open it by the machine's Tailscale name as well, a phone included once the Tailscale app is on it. A phone uses the HTTPS address below, so it can install the board as an app.

**Install it as an app.** In Chrome on the board's machine, open `http://localhost:8787` and click Install at the right of the address bar (or the menu, Cast, save and share, Install page as app). It opens in its own window, and its Dock icon shows the Needs you count. Chrome installs only from a secure origin. `http://localhost` counts as one. The board's plain-HTTP tailnet names do not (Chrome reports `not-from-secure-origin`), so on other machines and a phone it stays a browser tab until the board has an HTTPS address (see "Over HTTPS, for a phone"). `manifest.webmanifest`, `sw.js` and `icons/` make it installable. The icon is The Anvil Door: a shining silver arch on pillars, an anvil in outline, five stars and one ember spark, on deep night, in the manner of Middle-earth's door emblems. It is original art, drawn as vectors. `icons/icon.svg` is the tab icon, the sidebar's mark and the source of the PNGs. `icons/maskable.svg` is the same art full-bleed at 80%, for launchers that cut their own shape. `icons/build.sh` renders the four PNGs from the two with `rsvg-convert`, so run it after changing either. The manifest names the app The Forge and colors its title bar like the page. Chrome re-reads the manifest of an installed app on its own schedule and asks before it changes the app's name or icon. To take a new icon at once, remove the app (menu, Uninstall The Forge) and install it again. The service worker serves the page, its scripts and icons from the network first and falls back to its last copy when the board is down, so the app still opens and says it can't reach the board. It never caches `/api`. Browsers that refuse service workers (some built-in ones do) can't test installability, so check it with real Chrome (`Page.getInstallabilityErrors` over DevTools).

**Over HTTPS, for a phone.** Chrome on Android installs an app and runs a service worker only from a secure origin, and the plain-HTTP tailnet names are not one. `tailscale serve` gives the board one: `https://<machine>.<tailnet>.ts.net` (no port), which only devices on your tailnet can open, with a certificate Tailscale issues. Setting it up is your step, once, on the board's machine:

1. Put `"tailscale"` in `queueBoard.bind` beside `"127.0.0.1"` and restart the board (`queue-board/install.sh`). The board asks Tailscale for its names only when that word is there.
2. Run `tailscale serve --bg 8787` (your `queueBoard.port`). Tailscale then listens on port 443 of the machine's tailnet name and hands each request to `http://127.0.0.1:8787`, and it keeps doing so across restarts. If HTTPS is not on for your tailnet yet, the command says so and prints the link that turns it on. `tailscale serve status` shows the address, and `tailscale serve reset` clears the machine's serve setup.
3. On the phone, with the Tailscale app on, open that address in Chrome and choose the menu, Add to Home screen, Install. It then opens full screen like any app, with the bar along the bottom (see "On a phone").

The HTTPS address works on your other machines too. `tailscale status --json` prints the full name under `CertDomains`. The board reads it at start and asks again every ten minutes until Tailscale has one, so restart the board to take a new name at once. Three things in the board make it work behind the proxy:

- **The Host check** (`host-ok.mjs`). Every route but `/healthz` answers only to the names the board is reached by, as a guard against DNS rebinding. Behind `tailscale serve` the Host header is the machine's ts.net name with no port. The board takes that exact name from Tailscale (`CertDomains`) and accepts it with no port or with `:443`, and nothing wider: another domain, another machine's ts.net name, this machine's name under another tailnet, or `localhost` without the board's port all get 421. On its own port the board takes that exact ts.net name as well once it knows it. Until then it takes the machine's host name under any tailnet there. `node --test queue-board/host-ok.test.mjs` checks the rule.
- **Who is calling** (`callerOf` in `host-ok.mjs`). Through the proxy every request reaches the board from the board's own machine, so the socket's address alone would make a phone look local. Two routes care: "Open in terminal" opens iTerm only for a browser on the board's machine and hands anyone else the ssh command, and `/api/alert` takes the herald's calls only from that machine. Both read the caller from the proxy's `X-Forwarded-For` when the request comes from loopback or from one of the board's own addresses, and treat a proxied request without it as a stranger. A caller on another machine is judged by its socket, whatever headers it sends.
- **Nothing in the page names a host or a port.** Every fetch, the event stream and the service worker use paths from the root, so the same page works at either address.

The manifest has what Android asks for: a name, `start_url` and `scope` of `/`, `display: standalone`, theme and background colors, 192 and 512 PNG icons and a maskable 512.

## How it works

- `board.mjs` runs on the board's machine (`queueBoard.host`) under launchd (`dev.agent-queue.queue-board`, kept alive; `install.sh` installs it). It listens on the addresses in `queueBoard.bind`, `127.0.0.1` by default, so the LAN can't reach it. `tailscale serve` can put an HTTPS address for your tailnet in front of the loopback one (see "Over HTTPS, for a phone").
- When the page asks for data and the last snapshot is over 45 seconds old, it builds a new one. With nobody looking and the herald not running there is no work at all.
- A snapshot runs `collect.mjs` on each machine in `dispatcher.enabledHosts` (locally on the board's machine, over SSH on the others, to the destination in `queueBoard.ssh`), then reads the live tickets' PRs from GitHub in one GraphQL call and the queue labels and open asks from Linear in one call.
- `collect.mjs` reads the dispatcher's `state.json`, `PAUSED` and log, `fleet.sh ps`, each account's saved plan usage and the machine's load. It never runs `claude -p /usage`, so it can't crowd the dispatcher's own usage checks. The usage shown is as of the account's last refresh, and the page says how old it is.
- **Outside the queue** lists every other live background worker on the fleet's accounts: one some session started with `fleet.sh dispatch`, such as a rush ticket, with no queue ticket behind it. Nothing has to register it. `collect.mjs` takes every background session in `fleet.sh ps` that has a running process and that no queue ticket ever pointed at. It reads the worker's ticket from its branch or session name, its branch from where it runs (or the newest worktree on that ticket's branch when it started in the workspace folder), its start time from the session registry and its last activity from its transcript. The board then looks up its PR by branch and its title in Linear. The dispatcher counts a working one against its machine's `maxWorkers`, so the slot strip shows it in a slot, marked outside the queue. A finished one drops off a day after its last activity, and a blocked one shows under Needs you. View session and Open in terminal work the same as for a queue worker.
- **Bundles.** One worker and one PR can carry a lead ticket and up to two companions. A companion's state entry names its lead in `bundledInto`, so the board leaves it out of the list and shows it on the lead's entry instead: the slot and the card read "ABC-101 + ABC-102", and the card has a line per companion with its title. A bundle takes one slot, and its companions merge or go stuck with the lead, so they appear on the lead's row under Merged and Needs you too. `#session=<companion>` opens the lead's worker.
- **Queue-low watcher.** `queue-low-watch.mjs` polls the snapshot every 10 minutes and exits with a report when the free worker slots outnumber the ready tickets that wait on no blocker, on two checks in a row (45 minutes at least between reports). Slots held back by account headroom or load are listed apart, since more specs would not fill them. The orchestrator session runs it in the background and specs the next batch when it fires. `--once` prints the current state. `node --test queue-board/queue-low-watch.test.mjs` covers the counting.
- **Merge queue.** A green PR in main's merge queue shows "in merge queue" with its position (GitHub's `mergeQueueEntry`). It is in flight, so the board never flags it as stalled, and neither does `hourly-check.mjs`.
- **Cancelled duplicate checks.** A worker that pushes and then edits its PR seconds later can start two runs of a workflow that cancels its older run, and GitHub keeps both on the commit. The board drops a cancelled run when the same check has another run there, as GitHub's merge check does. Without that, a PR reads "Failing: Ticket ids in the PR title are complete" while its newer run has passed.
- **No daily cap.** The worker slots (`hosts.<name>.maxWorkers`) bound the queue.
- **Sentry slot.** A machine with `hosts.<name>.sentryWorkers` keeps side slots for Sentry fix tickets (label `linear.labels.sentry`), and the board counts them apart from the regular slots. A busy Sentry slot never makes the machine look over-full, and an idle one never shows as a free regular slot. A ticket in the slot (`sentry: true` in that machine's `state.json`) carries a Sentry marker on its bay, card and merged row. Each Fleet card shows its heartbeat age when it is stale, read from `heartbeats/<host>.json` in `paths.sharedDir`. When a Sentry host's heartbeat is over `sentryHeartbeatMinutes` old (45 by default) or paused, its slot reads offline, its card says Sentry tickets pass to the next machine in line, and Needs you flags it when the machine still ticks. This repo's dispatcher keeps the Sentry slot and takes a pluggable triage module (`sentryTriage` in the config; see the root `README.md` and `dispatcher/README.md`). It ships no triage of its own.
- **The Sentry cascade.** Every machine with `sentryWorkers` has a Sentry slot, and a Sentry ticket goes to the first machine in the order of `dispatcher.enabledHosts` whose heartbeat is fresh, unpaused and says it has Sentry room. `board.mjs` passes each heartbeat's `sentryRoom` and the cascade order (`snap.config.sentryCascade`). Each Fleet card's Sentry line says where the machine stands: "idle, first in line", "idle, no room" (amber: busy, low accounts, or the reviewer has the most Sentry reviews waiting), busy or offline. A Sentry ticket in the ready queue reads "for <realm>'s Sentry slot", naming the machine it goes to now, or "Sentry, waiting for room" when none has room.
- **Swap.** Each Fleet card has a Swap used bar, measured against the machine's RAM (a Mac grows its swap files as it needs them, so its swap total says little). It turns amber at a quarter of RAM and red at half, and the card then names the process holding the most memory, read with `top` on a Mac so compressed pages count. At half of RAM, Needs you flags the machine too. The dispatcher gates on memory free, which can read healthy while a machine pages all day: a machine with 39% free and 14 GB swapped on 24 GB of RAM type-checks at a crawl. `collect.mjs` calls `sysctl` and `top` by full path, since the board's ssh PATH has no `/usr/sbin`. Before that fix every remote Mac's memory read blank.
- **Worker nicknames.** Every live worker has a Middle-earth name, shown ahead of its ticket ID on its slot, its card, its Needs you items, its merged row and the session panel. The board reads `nickname` from each machine's state when the dispatcher gives a ticket one, and names the rest itself. A worker some session started outside the queue has no dispatcher, so `nameWorkers` in `board.mjs` names it from the `adhoc` pool, the wanderers (Gandalf, Radagast, Treebeard and others), and keeps the name in `queue-board-names.json` in `paths.stateDir` while it shows. It also covers a live ticket whose dispatcher has not ticked since it started. The pools live in the config under `queueBoard.nicknames`: a list of names per realm (`rivendell`, `shire`, `erebor`) or per host, plus `sentry`, `adhoc` and `other` (every machine of Rohan). The board reads them at start, so restart it with `queue-board/install.sh` after editing them. Labels that used to say "worker" use the name: the status chip ("Sam is busy", "Thorin failed"), the slot and card status ("Gimli is gone, no PR"), the Needs you text ("Sam is waiting on input in its session"; the "Worker ended" item is now "Ended"), and the session panel's speaker labels and message box. A worker with no name yet reads "the worker".
- **Usage resets.** Under each 5-hour and weekly percentage, for the Claude accounts and for Codex and Grok, the card shows when the window resets as a clock time (with the weekday unless it is today) and a countdown. A reset that has already passed means the reading is from the window before it: the percentage is dimmed and the countdown says how long ago. That is common, since an account's usage is only as fresh as the dispatcher's last `/usage` check on it.

The board spends no Claude tokens. It uses the same Linear key and GitHub login as the dispatcher. It writes its own marks (Handled, worker names) in `paths.stateDir`, the sound settings and the herald's status file, and, only when you pull a lever in the Fleet view, the config's `dispatcher` section, the change log and wake requests (see Fleet).

## On a phone

The phone layout lives in three files, so `page.html` stays as it is for a desktop window: `mobile.css` (the frame), `mobile-views.css` (each view) and `mobile.js` (the More sheet, the tap notes and the maps' touch). `page.html` links the two stylesheets first in `<body>`, after every style in `<head>`, so they win at equal weight. One media query decides "phone": a window up to 899px wide, or a touch screen up to 540px tall lying on its side (a large phone on its side is wider than 899px). A desktop window matches neither, and `mobile.js` asks the same query before it does anything.

- **The bar.** The sidebar becomes a bar along the bottom, in thumb reach and always in the same place: Queue, Sessions, Inbox, Middle Earth and More. The three counts you act on ride on their tabs as wax seals. More opens Fleet, Worktrees, the Top view and the sound controls (Music, Next track while it plays, Mute sounds, Sound settings) as a sheet rising from the bar. A sound item keeps the sheet open and shows its new state. More carries a small seal when a view behind it is hot.
- **The header** scrolls away with the page. It holds the view's name and the data's age.
- **Touch sizes.** Every control is at least 44px tall where the thumb lands. A button grows to that. A chip, a ticket link or a link in a line of text keeps its look, and its touch area grows around it.
- **Nothing is cut to an ellipsis.** A title takes its own line under its ID and wraps in full, chips wrap, and a card's command wraps. Text that a desktop shows on hover (a chip's reason, a time's full date) shows in a small note when the element is tapped, and the next tap or a scroll puts it away.
- **Queue.** Needs you first, as on a desktop. The whole Queue is about three screens. Ready and Merged rows put the ID, chips and age on one line and the title under it.
- **Fleet.** Cards stack one to a row, an account letter is a 44px target, and the accounts table becomes a list: the account, its email and its week left on one line, then its mark and 5-hour left.
- **The session panel** is the whole screen: the close button and Send are 44px, the chips scroll sideways in one line, and the feed takes what is left. The page's viewport shrinks when the keyboard opens (`interactive-widget=resizes-content`), so Send stays above it.
- **The sound settings** are a sheet along the bottom, over the bar, with 44px sliders, switches and Test buttons.
- **The two maps.** A map is never shrunk to fit: at the smallest scale that keeps a figure readable (2) the side view is about 970px wide and the map from above 960 by 600. So each map sits in a frame and the finger pans it, sideways in the side view, sideways and up and down from above. Upright, the frame is what is left between the header and the bar. It opens on the worker to act on first: whoever just called, else the first one blocked on you, else the first worker. Names are 11px, and a name's touch area is 44px tall. A tap opens that worker's session panel, which holds everything the hover text has. The key is one line that scrolls sideways. From above, the world is always the full plan (480 by 300 units). A plan squeezed to a narrow screen throws at some heights (placing the eyries at one, an array of infinite length at another), and a phone never has room for the full one, so there it pans.
- **On its side** the bar stands along the left edge, so the page keeps the screen's whole height. A map's frame is then the whole screen, and the page scrolls down to it when the view opens. The header is one swipe up.
- **Safe areas.** The bar, the sheets, the session panel and the header pad themselves by `env(safe-area-inset-*)`, and heights use `100dvh`, so nothing sits under a gesture bar or a camera cutout when the board runs as an installed app.

To check a change, open the board headless at 360, 384 and 412 wide and at 824 by 384, and look for a layout wider than the screen, a control under 44px and text under 11px in every view, the session panel, the sound settings and the More sheet.

## Session panel

**View session** on a building card or a "Needs you" item opens that worker's session: its recent history and a box to message it.

- **History** comes from `history.mjs`, run on the worker's machine. It reads the session transcript (`<account dir>/projects/*/<session id>.jsonl`) from the end and lists user and worker messages, each tool call with its description and command, failed tool results and error notices. Successful tool output is left out. The panel refreshes every 10 seconds while open, and **Show earlier** reaches back 400 entries.
- **A Codex or Grok worker** has no Claude session, so its panel shows its runs instead. The board shows such a worker when the dispatcher reports one (`driver: 'engine'` in its state entry, with the engine, the round and the engine's name as the account). This repo's dispatcher does not start Codex or Grok workers yet, so with it no such panel appears. The panel reads each round's files from the worker's registry folder on its machine: the brief it was given, the engine's own event stream and its question when it stopped to ask. It gives them in the shape of `history.mjs`: each round opens with its brief, then the engine's messages, each command and file edit, the tail of any failed command, a "Fix round N" marker between rounds, and an open question last. Neither engine's stream carries times, so only a round's start has one. Its card has View session too, and its seat opens the panel. The panel shows no account chip (the mark by its name says what runs it) and no message box, since it reads its brief and takes no messages.
- **Sending** runs `send.py` on the worker's machine. It opens the session with `claude attach` in a pseudo-terminal, pastes the message, presses Enter and disconnects, so the message arrives as your own turn, the same as typing it after `claude attach`. An idle worker reads it at once. A busy one reads it at its next step. A worker blocked on a prompt is refused, since Enter would pick an option there. Answer it with **Open in terminal**. The board log records each send (ticket, worker, length, outcome) but not the text.
- The panel looks the worker up from the dispatcher's own state by ticket ID. The page never names a machine or account. Every route but `/healthz` answers only to this board's own host names (127.0.0.1, localhost, its machine's host name, the addresses in `queueBoard.bind` and its Tailscale names), and sending also needs a JSON body and the `X-Board: send` header, so another website can't trigger it.
- **Its address.** `#session=ABC-123` at the end of the board URL opens that ticket's worker panel, and `#sessions/local_<id>` opens a Claude app session's panel over the Sessions view. The open panel marks its worker's card and its calls in the Middle Earth bar. Closing a panel opened from a link clears the address.
- **Inside the panel**: the worker's PR and where it stands, **Open in terminal**, and the details the old building cards carried (the last push, the worker's id and the attach command).
- **Calls open what called.** The eagle and the call bar open a Claude app session in the Claude app (`claude://code/continue`) when the page runs on that session's Mac, and its board panel anywhere else. The board says which Mac the page runs on in `viewerHost`. A worker's call opens its panel, a machine's call its Fleet card, main red its failing run, and an ask or a reminder Needs you.

## Inbox

The Inbox view shows your unread Linear notifications, so a mention or a reply doesn't wait until you ask a session about it. The board's Linear key is your own account, so Linear's `notifications` query returns your inbox. `linear-inbox.mjs` reads it in one GraphQL call (the newest 250 notifications, plus the newest 100 mentions, assignments and review requests so an older mention isn't pushed out), in the background at most every 20 minutes while the page is open. That costs about 1,900 of Linear's 3,000,000 hourly complexity points per read.

- **Mentions, replies and reviews**: someone mentioned you, replied to one of your comments, or asked for your review. The sidebar's Inbox badge counts these.
- **Assigned to you**: issues newly assigned to you.
- **Comments on issues you follow** and **Other updates** (status changes, due dates, PR checks): one row per issue with the newest notice and how many there are. The newest 40 issues of each travel in the snapshot. Linear has the rest.

Each item links to the comment in Linear. **Copy for Claude** copies the notice and its link to paste into a session. It shows when the pointer is over the item or the keyboard is on it, and always on a touch screen. The view only reads: a notice leaves it once you open or archive it in Linear and the next read comes round. Snoozed and archived notices are left out. An inbox can hold hundreds of unread notices, most of them comments on followed issues and status changes, which is why the ones aimed at you come first.

## Sessions

The Sessions view is for the Claude app sessions you run by hand, outside the queue: on a busy day ten or more go back and forth, and the ones that end waiting on you get forgotten. The Claude desktop app keeps a record per Code session in `~/Library/Application Support/Claude/claude-code-sessions/**/local_*.json` and rewrites it as the session works. After each turn it adds a summary: a category (completed, review_ready, blocked), a one-line detail and, when the session needs you, what it needs in its own words (`needs_action`). The record also says when you last opened the session (`lastFocusedAt`), when its last turn ended (`lastTurnEdgeAt`), the session that started it (`spawnedFrom`), the routine that ran it (`scheduledTaskId`) and any error. `sessions.mjs` runs on each machine that has the Claude app and reads the records of the last 14 days that aren't archived. A machine without the app (a Linux box, say) shows no sessions. The script only reads the app's files. Older records are only counted, from a cache of each file's archived flag by modification time (`queue-board-sessions-cache.json` in `paths.stateDir`), so a scan takes about 0.3 seconds once warm. The board runs it in the background at most once a minute while the page is open.

Each session gets one group, in this order:

- **Working now**: a turn under way (activity after its last turn edge, no summary for its latest reply yet).
- **Waiting on you**: its last turn ended needing you, and the row shows what it needs. A session whose last turn never finished and has been silent for 10 minutes joins it as **stopped mid-turn**, most likely on a question or permission prompt in the app.
- **Ready for your review**, **New since you looked** (it did something after you last opened it) and **Errored**.
- **Quiet for 2+ days** and **Done and seen**.

Only **Waiting on you** and **Ready for your review** stay open. Every other group is one line that opens in place. A row shows only its open PRs.

A routine shows only its latest run. A side session carries a "from <parent>" chip. A dot before the title marks a session that changed since you last opened it. **Handled** hides a row until its session does something new. `board.mjs` keeps the marks in `queue-board-handled.json` in `paths.stateDir` (machine and session, with the activity time they covered), and **Show N marked handled** brings them back. The sidebar's Sessions badge counts the sessions waiting on you that aren't handled. The group says "Waiting on you" so it never reads as the Queue's own "Needs you". **View** opens the session's transcript in the session panel, read-only: the app runs its sessions on the fleet's primary account (`fleet.primaryAccount`), so `history.mjs` reads them as it reads a worker. Replies, archiving and starring happen in the Claude app. The board changes nothing there.

## Worktrees

The Worktrees view lists every git worktree on each queue machine, so a cleanup can see what is safe to remove. `worktrees.mjs` runs on each machine and reads every repo directly under each folder in `queueBoard.repoRoots` (the workspace folder by default). For each linked worktree (the main checkout is left out) it reads the branch, the last commit, how many tracked files have uncommitted changes, how many commits are on no remote branch, and which processes have their working folder inside it (`lsof` on a Mac, `/proc` on Linux). The board then looks up each branch's newest PR on GitHub, one GraphQL call per repository (`worktree-state.mjs`), and gives each worktree one state:

- **In use**: a process is working in it, or a live worker builds its branch.
- **PR open**, **Merged**, **PR closed**: its branch's newest PR.
- **Not pushed**: no PR, and it holds work that is nowhere else.
- **No PR**: no PR, and nothing in it that GitHub lacks.
- **Folder missing**: git still lists it but the folder is gone (`git worktree prune` clears these).

A merged or closed worktree with no uncommitted changes and no commits missing from GitHub counts as **safe to remove**. Commits on no remote branch still count as saved when the worktree's head is the PR's head, which is what a squash merge that deleted the branch leaves behind. Each machine lists the rest first, with its counts in plain text, and folds the safe ones into one **Show N safe to remove** line. A row names its repository only when it is not the main one.

A row of chips at the top picks one machine (`#worktrees/<host>`) or All (`#worktrees`). **Forgotten** narrows either to what Gollum hoards (`#worktrees/forgotten`, `#worktrees/<host>/forgotten`): worktrees nobody uses whose last commit is 3 days old, or 7 with a PR open, oldest first (`grForgotten` in `gollum-data.js`). Clicking a Gollum or his hoard in either map opens his machine's forgotten worktrees.

The scan runs in the background at most every 10 minutes while the page is open. It only reads: git runs with `--no-optional-locks`, so it never takes the index lock a worker needs, and with `core.preloadIndex=false`, which cut its CPU cost about six times (about 0.1 seconds per worktree). Untracked files are not counted, since finding them cost about four times as much, and `git worktree remove` refuses a worktree that has any. Temporary worktrees in the system temp folders (a jscpd check makes one) are left out.

**Orcs.** While a worker's PR has a failing CI check, an orc comes down from the back of its realm and they fight across the open ground near its station (`scene-duel.js`), on the strip between the two rows so they never walk through a landmark or cover another worker's station, and keep inside the realm. **Only CI brings an orc.** Two things once put orcs on workers whose sessions showed CI running fine. The Claude review's own checks counted as CI: after each push the review check can conclude FAILURE with "Re-review not requested: this head has no review" until a re-review is requested, and that placeholder looked like a failing job. **The Great Eagles.** A call from a Claude app session (the orchestrator's, say) brings a Great Eagle instead of a messenger: it flies down out of the sky, banks, flares and lands on a crag at the back of the road in the realm of the session's machine, a scroll in its talons. The eagles are giants, as in the books: 25 units tall perched (an elf is 15) and about 63 across the wings, on a crag that road walkers pass in front of and workers walk round. **Gollum.** A unique character with a purpose of his own: one per machine, with no tag. He hoards what is forgotten and covets usage, by `gollum-data.js`'s rules (see Worktrees and Fleet above). Every realm whose machine has forgotten worktrees or a Claude account at 90% of a window has its own Gollum at its own hiding place (Rivendell's pool under the falls, behind the Shire's hill, Erebor's dark doorway, behind Rohan's stables), each with his own seed so they never move in step. He creeps out and rocks and mutters over a little hoard that grows with his machine's count (up to nine trinkets), and clutches the Ring instead while an account signed in on his machine is past 90%. A realm with nothing to report shows no sign of him. A click on him or his hoard opens his machine in the Gollum view. He is mostly out at night, his eyes shining. He scuttles home when an eagle comes down in his realm or the Eye's beam comes near, and in Rivendell he snatches at a fish now and then. Code: `scene-gollum.js` (one Gollum per host in `gols`), `scene-gollum-tag.js`, `sprites-gollum.js`.

**Saruman, the seer of the Codex and Grok calls.** Your sessions can hand research to Codex and Grok through `scripts/ext-agent.sh`, and the board counts those runs on the board's machine every 15 seconds (`ext-runs.mjs`; every snapshot carries them as `seer`). While any runs, Saruman stands at the far west end of the road (Isengard lies west) gazing into a palantir on a dark pedestal, his white robe shimmering through all colours as in the books, with white hair and beard, black strands about the lips and a black staff. The stone glows in the seeing-stones' colours: blue for Codex, amber for Grok, crossing between them when both run, brighter and busier the more calls run, and reddening as that subscription passes 80% of its weekly use. At night it lights his face from below. When the calls end he lingers 25 seconds, then walks off and leaves the pedestal dark. His tag reads "Saruman · 5 Codex · 5 Grok" (the counts of the calls running), and a click opens the Machines view. Code: `scene-saruman.js`, `sprites-saruman.js`, `sprites-saruman-stone.js`.

**The marks of Claude, Codex and Grok.** `ai-marks.js` draws each as a small logo the size of the text around it: Claude's spark in its orange (Simple Icons' "claude", CC0 icon data), Codex's blue cloud with a prompt (cut from the Codex app's own icon, its white field made clear) and Grok's mark (Wikimedia Commons' "Grok-icon.svg", CC0, without its black square, drawn in the text colour so it shows in both themes). Every worker's label carries the mark of what runs it: its tag in both Middle-earth views, its Queue slot, card, Needs you row and session panel title, and its Machines seat. The Accounts card's group headers are the marks alone, Saruman's tag counts his calls under them, and a Claude app session's replies in the panel are signed with the spark. Words stay in sentences and tooltips.

**Codex and Grok as queue workers.** The board draws Codex and Grok workers as ordinary workers when the dispatcher reports them. This repo's dispatcher does not start such workers yet, so on a stock install none appears. The rules the board follows are these. A dispatcher that ranks Codex and Grok with the Claude accounts hands a ticket to the one with the most weekly usage left. An engine that wins runs the ticket as a full worker with no Claude session behind it: it builds, pushes, opens the PR, then works one round per CI or review fix. Its state ticket carries `driver: 'engine'`, the engine, the round, and the account as the engine's name, and each such worker keeps a registry file on its machine. `collect.mjs` reads those files on each machine and `board.mjs` turns the ticket into a worker (`engine-workers.mjs`): busy, done, blocked (with the worker's question), limit (the engine's plan limit) or failed. The file is read first, since the worker writes it the moment its state changes. The ticket's `engineStatus`, which the dispatcher copies from it once a tick, stands in when the file can't be read. A busy row whose process has died reads as failed once the file is two minutes old, and a ticket the dispatcher's containment audit stopped shows as failed. These workers are named from their machine's own pool and drawn as its own folk, like any worker, because one is just a subagent executing work and needs no different look. Only the engine's mark by the name says what runs it, and from the second round on the round follows the name (`R2`). A blocked one raises a hand, one at its limit sleeps under the red bubble, a failed one fades, as fleet workers do. View session shows its runs (see Session panel). Saruman never sees them: `ext-runs.mjs` counts an `ext-agent.sh` run only when no process above it runs a build worker, and only a wanderer outside the queue named Saruman sends him from the tower. They hold a slot in their machine's pool like any worker and count in "N of M building" against `maxConcurrent`. Each machine has one pool, `hosts.<name>.maxWorkers`, shown as its regular slots in the Queue and the Machines view. There are no engine seats. `collect.mjs` reports which engines the dispatcher may use as `engineAccounts`. The same rule holds for every worker: only a ticket still building holds a slot on its machine, and a PR waiting on the orchestrator's merge or parked on the reviewer's review holds none. Such a worker stays on the board, after the slots with a dashed outline and a note saying what it waits on, and in the Middle-earth views it keeps its station. A merge-asked ticket still counts in "N of M building"; a parked one does not.

**One computer, the whole map.** With one queue machine there would be one realm. `queueBoard.spreadRealms` ("auto" by default, which is on when exactly one host is enabled; true or false force it) lets a machine also hold the realms no machine holds, so one computer fills all four (`realm-spread.mjs`). Every live ticket carries `realm`, a realm key: its machine's own realm normally, and with spread on the realm of its machine with the fewest live workers when the ticket starts, kept for the ticket's life and after the merge (`<stateDir>/queue-board-realms.json`). Regular workers, Sentry riders and wanderers are balanced apart. A worker's name comes from its realm's pool (`worker-names.mjs`). The snapshot says `config.spread` and lists each host's realms in `config.spreadRealms`. Only the two Middle-earth views draw it: they read `drawSnap()` (`realm-view.js`), which with spread on makes each realm a machine of its own, with its own id (the machine's own for its first realm, `host~realm` for the others), its share of the worker and Sentry slots (the shares add up to the machine's own), the tickets given that realm and the real machine's health. The bridges back to the real machine: a call finds its worker in the realm it sits in (`drawWho`), a session's or machine's call and the one Gollum stay with the first realm and open the real machine's pages, the out-of-reach note shows once, merges set off fireworks over the realm their worker sat in and the herald plays that realm's cue, and every click opens the real ticket's session panel. The Queue, Machines, Worktrees, Sessions and Gollum views, the header's slot counts and the session panel keep the one real machine; a worker's portrait there wears its realm's folk. `npm run test:page` checks eight workers on one machine drawing two to a realm in both views, a worker keeping its realm and name over ten snapshots, the clicks, the slot totals, and one realm with spread off.

## Sound

You want to hear it when an agent needs you while you work in something else, so sound is on by default and has a mute for calls. One service plays every alert, so nothing sounds twice and no browser has to be open.

- **The herald** (`herald.mjs`) runs on a Mac under launchd (`dev.agent-queue.queue-herald`, kept alive, installed by `queue-board/install-herald.sh`). Every 20 seconds it reads the board's `/api/snapshot`, works out what changed (`herald-events.mjs`), plays each new event's cue with `afplay` (warning the board 400 ms first, so the music ducks; see Music) and posts a macOS notification titled "Middle-earth" saying who and what ("Frodo is blocked · ABC-123", "Orchestrator session is waiting on you"), with the Forge's icon (see below). Its first read after a start only takes note, so a restart never sounds a burst. A source the snapshot can't speak for (a machine the board never reached, Linear or GitHub failing, sessions not scanned yet) keeps its last state, so its return is no news either. When the board stops answering, the herald keeps trying quietly, posts one notification after 5 minutes, and on the board's return starts from a fresh baseline and says how much waits. Because it reads every 20 seconds, the board refreshes its snapshot about once a minute around the clock while a herald runs. Another Mac can run its own herald against the board's machine (`queue-board/install-herald.sh --base http://<board-machine>:8787`). Its log is `queue-herald.log` in `paths.stateDir`.
- **The notifications carry the Forge's icon.** macOS puts the posting app's icon on a notification, and one sent through `osascript` carries Script Editor's. So the herald posts through its own small app, Forge Herald (`herald-notifier.swift`, about 60 lines of Swift on the UserNotifications API), which `install-herald.sh` compiles into `Forge Herald.app` (in `paths.stateDir`'s `queue-board` folder, or where `queueBoard.heraldNotifierApp` says) with `icons/forge.icns` and signs locally. macOS asks once whether Forge Herald may post. Until it is allowed, on a Mac with no Swift compiler, or whenever the app fails, the herald posts through `osascript` as before and says so once in its log, so no notification is lost. Two things macOS insists on: the first launch has to go through LaunchServices (`open`), or the request is refused with "Notifications are not allowed for this application" and no prompt (the log shows usernoted "Failed to find or validate client"); and closing the prompt without Allow counts as a no, which only System Settings > Notifications > Forge Herald can undo. An AppleScript applet with its own icon was tried first and posts nothing on macOS 26. `forge-herald --status` prints allowed, denied or not-asked.
- **A click opens what the notification is about** (`herald-links.mjs`). The herald passes a link to Forge Herald, which opens it on a click. A worker blocked, waiting, stuck, failing CI or asking for a merge opens its session panel (`#session=ABC-123`). A Claude app session waiting on you opens in the Claude app on the Mac it runs on, and its board panel (`#sessions/local_<id>`) anywhere else. A machine out of reach or paused opens its Fleet card (`#fleet/<host>`), main red its failing run, and the reminder Needs you. A merge and main going green play their sound and post no banner. The board's address comes from the snapshot (`board.url`): its `tailscale serve` HTTPS name when that serves the board's port, else the machine's name. So a link works from any device. A click through `osascript` opens nothing.
- **Events and cues**, each its own sound:

| Event | When | Cue |
|---|---|---|
| Needs you | a worker newly blocked on input, a ticket newly carrying an open ask, a PR newly waiting on your merge, or a Claude app session newly waiting on you or stopped mid-turn and not marked handled | a two-tone hand bell |
| Reminder | every 30 minutes (settable) while anything waits on you, with how many and the oldest | three soft taps on a bar |
| Trouble | a ticket newly stuck, a machine out of reach for two snapshots in a row, a machine newly paused | a low tower bell, tolled twice |
| CI failing | a live PR's checks newly failing, when an orc appears in Middle-earth | a short orc drum |
| Merged | a ticket merged, in its realm's voice | Rivendell a harp run, the Shire a whistled jig, Erebor a dwarvish horn call in B-flat, Rohan a horn of the Mark in F (a fifth machine too) |
| Main red | main turns red or gets a new red commit, and every 15 minutes while it stays red | the war horn |
| Main green again | main recovers | a short victory call |

  Several at once play in the table's order with main red first, at most three cues a cycle, and notifications past four fold into one.
- **The cues are code.** `sounds/make.mjs` synthesizes each one with `sounds/dsp.mjs` (struck partials for the bells, a plucked string for the harp, a whistle, and horns) into `sounds/*.wav`: mono 16-bit, matched in loudness, melodies written for this board. `node queue-board/sounds/make.mjs` writes the same files again.
- **Mute and the settings live in one file**, `sound.json` in the `queue-board` folder of `paths.sharedDir` (or where `queueBoard.soundFile` says). The shared folder carries it to every Mac that runs a herald, and the herald reads it every cycle (`sound.mjs` checks every field; a missing file means the defaults). The horn button at the sidebar's foot (`side-dock.js`) drives the mute control (`horn.js`), which writes it through `POST /api/sound` (the same X-Board header rule as `/api/send`), so it silences the herald on every Mac while the notifications still post. Muted reads in red with the horn struck through. **Quiet during Zoom**, on by default: while Zoom's meeting process (`CptHost`) runs on the herald's Mac, the herald stays silent and the horn reads amber. The settings button beside it opens the settings (`sound-ui.js`): the alert volume, a switch per event (off means no sound and no notification for it), the reminder interval, the music volume, Zoom auto-mute, a Test button per cue that the board plays on its own machine, muted or not, and one line saying whether the herald is running. The herald writes its state every cycle to `herald-status.json` in the same `queue-board` folder under `paths.stateDir` (or where `queueBoard.heraldStatusFile` says), which `GET /api/sound` serves. The settings button turns amber while the herald is stopped or can't read the board.
- **Music.** The play button at the sidebar's foot plays your own MP3s as one continuous mix whenever you turn it on. `music.mjs` streams them from the folder in `queueBoard.musicDir` (`~/Music` by default; the `QUEUE_BOARD_MUSIC` environment variable in the board's launchd plist names another folder), one folder per album or flat. The files are yours: the board only reads them, and they are never copied into this repo, the shared folder or anywhere else. `music.mjs` lists every MP3 under that folder at `GET /api/music`, rescanning at most every 5 seconds, so a new album folder joins on its own, and streams one at `GET /music/<id>` with HTTP Range, so seeking works in Chrome and Safari. An id is a hash of the file's path, looked up among the files the scan found, so no path from a request reaches the disk. Links inside the folder are skipped. Titles come from the file names with the disc and track numbers dropped and a stand-in underscore after a title word put back as a colon ("Prologue_ One Ring" reads "Prologue: One Ring"). The player (`music.js`, its CSS in `page.html`) sits just before Mute in every view and keeps playing across views: Play pauses and resumes, **Next** skips, and while it plays it shows the track, its album and a thin progress line (on a phone, the title only). It shuffles every track, none repeated until all have played, then starts a new order, and fades each track into the next over 4 seconds on two audio elements. **Music volume** in the sound settings is its own, 40 by default, saved in `sound.json` beside the alert volume. Mute, or the herald's quiet for a Zoom meeting, fades it out and pauses it. Unmuting brings it back only if it was playing. The order, the track and its place stay in the browser's localStorage, so a reload carries on (a plain tab waits for the first click or key), and one tab plays at a time: starting it in one stops it in any other. The Mac's media keys play, pause and skip it. The service worker never caches `/music` or `/api/music`.
- **Alerts come before the music.** If the music is playing, the alerts supersede it. Before each cue the herald tells the board it is coming and how long it lasts (`POST /api/alert`, accepted only from the board's own machine with the X-Board header; each cue's length is read once from its WAV header), waits 400 ms and plays it. The settings' Test buttons warn the same way. The board passes the warning at once to every page playing music on an event stream (`GET /api/events`, open only while that page's music is on or its Middle-earth view is open, so other tabs hold no connection). The warning also carries whose calls the cue is for (see Who is calling). The music (`music-duck.js`) fades to silence within 0.3 seconds, before the cue starts, stays silent for the cue's length and a second more, and fades back in over 1.5 seconds. Another alert in that time stretches the silence. The fades run on the audio clock, so the silence always ends by itself, and the stream reconnects by itself after the board restarts. The warning never holds a cue back: a board that is down, slow or broken costs the cue at most those 400 ms.
- **The page plays no alerts.** The page plays only the music you start. The dispatcher's own desktop notifications are off by default so each alert arrives once, from the herald. Its Slack posts are unchanged.
- **Tests.** `node --test queue-board/herald.test.mjs` covers the event rules, reading a cue's length from its WAV header, and the warn-then-play order, including a board that is down, hangs or throws.

## Fleet

The Fleet view (`#fleet`) shows each queue machine and every account in one place, with levers to run the fleet from the page. `#fleet/<host>` scrolls to one machine's card. The page is `control-data.js` (reading `/api/control`, sending one change at a time, the steppers, the confirmation and the toast), `control-fleet.js` (the top strip, waiting tickets, settings and the change log), `fleet-card.js`, `fleet-accounts.js`, `fleet-logic.js` (the sums, tested in `fleet-logic.test.mjs`), `control.css` and `fleet.css`. From the top:

- **The strip** says whether new work flows, the one worker count, with how many are over, and how many machines are paused. **Hold new work** sets `dispatcher.holdNewWork`: no machine that reads the change claims a new ticket, and everything already claimed carries on, merges included. **Let new work flow** turns it off. Under it sits every change that ends by itself, with a countdown, **End now** (put the old value back now) and **Keep** (drop the end time, keep the value).
- **Waiting for a slot** shows only while a ticket waits in a machine's wake queue, from the snapshot or, for a machine the board cannot reach, its heartbeat. **Push through** writes the same `wake-requests/<ID>.json` in `paths.sharedDir` that `dispatcher.mjs wake` writes.
- **A card per machine.** A slim band in the realm's colour with its sigil, the realm's name, the machine's name, a state word only when it is not simply ticking (Offline, Paused, Winding down, Safe to reboot), and when it last ticked. The heartbeat's age shows only when it is stale (`tickWords` in `fleet-logic.js`). Then the seats: a pixel figure per worker with its status gem, and a click opens its session panel. A dashed seat holds no slot, and an empty dashed seat is a free slot. Then **Workers**, **Sentry** and **Burst** as steppers (`maxWorkers`, `sentryWorkers`, `burstWorkers` in `dispatcher.hosts.<host>`), each beside what it governs. Then the health bars for load per core, memory free and swap used. Then the account letters the machine may use (`dispatcher.hosts.<host>.accounts`): on, off (a letter it has a folder for but does not use), red when signed out there, struck through when out of the queue. A click puts a letter on or off the list. At the foot **Wind down** (or **Bring back**), **Pause** (or **Resume**), and its worktree count, which opens the Worktrees view on that machine. A machine with no `dispatcher.hosts` entry shows its counts without steppers.
- **Wind down** sets the three slot counts to 0 and keeps each old value beside it as `<key>BeforeDrain`. The card then lists what still works there. It says "Safe to reboot" only once a fresh reading shows the machine reads no slots in its own copy of the config, and **Bring back** restores the kept values. The steppers lock while it is wound down. **Pause** and **Resume** run `dispatcher.mjs pause|resume` on that machine, which also stops its merges.
- **The accounts table** (`fleet-accounts.js`). On top the default model, effort and the model per ticket size. Then a row per Claude account: its email and plan, the machines it runs on, its week left with the reset, its 5-hour left, one mark (taken out, signed out on a machine, or past 90% of a window, which is Gollum's Ring from `gollum-data.js`), and its levers: **Burn** (`burnAccounts`; an end time also goes into `burnUntil`), **Fable** (`fableAccounts` and `noFableAccounts`; turning it on offers to burn the account in the same write), **Cap** (`workerCapByAccount`, showing the fleet's `workerCap` until it has its own), and **Take out** or **Put back** (`accountsOut` remembers which machines it was on; refused while an enabled machine has no account list, since it may use every account). Burn and Fable are separate switches. An account the board only watches follows, marked "not in the queue", then Codex and Grok with their week. **Floors and reserves** fold away at the foot. Under 900px the table becomes a list with Burn, Fable and Take out.
- **Folded at the bottom:** **Fleet settings and load guards** (`maxConcurrent`, the daily cap, Codex and Grok as accounts with which go first and their round cap, Codex free resets, Sentry triage, and each machine's own load limit and memory floor), **Dispatcher logs** (each machine's recent log) and the **Change log**, newest first. How a change behaves (which machines it reaches, the guards on the write, the record and end times) is in `levers.md`.

**A watched Claude account** shows in the accounts table, marked "not in the queue", but never gets queue work. It is a Claude Code folder `~/.claude-board-<name>` on any machine, signed in once by hand with `CLAUDE_CONFIG_DIR=~/.claude-board-main claude auth login --email <address>`. The hyphen in the name keeps it out of the fleet: `fleet.sh` takes only `~/.claude-<letters and digits>` as accounts. `collect.mjs` reads its saved usage like any account's (its `watched` list), and `watch-usage.mjs` keeps that fresh every 15 minutes.

## Codex and Grok

**A signed-out Claude account.** An account's profile file keeps its email after its login is gone, so the board takes sign-outs from the dispatcher's own check (`fleet.sh accounts` each tick, the dispatcher's `signedOut`). Its letter on the Fleet card turns red, the accounts table marks it, and Needs you folds every signed-out account into one row that says how to sign it back in: account a is that machine's own login (`claude auth login` in a terminal there), any other goes through `fleet/setup/add-account.sh`. The mark clears on the dispatcher's next tick after it signs in.

The Fleet accounts table's Codex and Grok rows show those plans. `ext-usage.mjs` asks each CLI the way its own usage screen does: Codex through `codex app-server` (`account/rateLimits/read`) and Grok through `grok agent stdio` (`_x.ai/billing`, plus `_x.ai/auth/info` for the account email). These are read-only billing calls. Neither starts a session or runs a model, so a reading spends none of the allowance it reports, and the CLIs keep their own sign-in. The board runs it on every machine once an hour, in the background, and merges machines signed in to the same account into one row. The machines can be on different accounts. A machine whose CLI is signed out gets its own row with the error. `queueBoard.extUsage: false` turns it off when you have neither CLI.

## Trying a change

Run a second board with `QUEUE_BOARD_DRY=1` to try a board change without touching the queue. A dry-run board refuses every POST (`dry.mjs`): it sends no message to a worker, opens no terminal, marks nothing handled, changes no sound setting and pulls no lever. Every view still draws, and every lever click gets a "dry-run board" toast.

```
QUEUE_BOARD_DRY=1 QUEUE_BOARD_PORT=8792 AGENT_QUEUE_CONFIG=<a copy of your config> node queue-board/board.mjs
```

Give it its own port, and point `AGENT_QUEUE_CONFIG` at a copy whose `paths.stateDir` and `paths.sharedDir` are scratch folders, so its own marks, log and wake requests stay apart. `levers.md` says how to try the Fleet levers against the copy. The herald takes `HERALD_NOTIFIER=<path to forge-herald>` to post through a notifier built with `install-herald.sh --staging-notifier`.

## Commands

```
queue-board/install.sh                           # install or restart the launchd job (the board's machine only)
queue-board/install.sh --remove                  # stop it and delete the job
curl -s http://127.0.0.1:8787/api/snapshot | jq  # the raw snapshot
tail <paths.stateDir>/queue-board.log            # its log (~/.agent-queue by default)
queue-board/install-herald.sh                    # install or restart the herald (add --remove to stop it)
tail <paths.stateDir>/queue-herald.log           # the herald's log
node --test queue-board/herald.test.mjs          # the herald's event rules
node --test queue-board/host-ok.test.mjs         # which Host headers the board answers to
node --test queue-board/herald-links.test.mjs    # where a click on each notification goes
node --test queue-board/worker-count.test.mjs    # the one worker count and the burst rule
node --test queue-board/queue-view.test.mjs      # the Queue's Needs you rows
node --test queue-board/fleet-logic.test.mjs     # the Fleet view's sums
node --test queue-board/control*.test.mjs        # the Fleet levers' server: what it accepts, refuses and writes, and end times
node queue-board/sounds/make.mjs                 # render the cues again
```

Run the scripts from the checkout that should keep running: the launchd jobs point at the files in the checkout that installed them. Both installers read `agent-queue.config.json` (or the file `AGENT_QUEUE_CONFIG` names) and fill in the plist templates (`queue-board.plist`, `queue-herald.plist`).

`page.html`, the view scripts (every `.js` file in `PAGE_SCRIPTS` in `board.mjs`), `sw.js`, `manifest.webmanifest` and `icons/` are read on every request, so page edits show on reload, in the installed app too. A new view script needs its path added to `PAGE_SCRIPTS` (and `queue-board/install.sh` run again), to `sw.js`'s `SHELL` and to `page.html`'s script tags. A new file under `icons/` or a new stylesheet needs its path added to `APP_FILES` in `board.mjs`, and a stylesheet to `SHELL` too. `collect.mjs`, `history.mjs`, `send.py`, `ext-usage.mjs`, `worktrees.mjs` and `sessions.mjs` run fresh each time on each machine, from the checkout at `queueBoard.remoteRoot` (the same path as the board's checkout by default). Edits to `board.mjs`, the `control*.mjs` modules, `host-ok.mjs`, `music.mjs`, `linear-inbox.mjs`, `worktree-state.mjs` or `sound.mjs` need `queue-board/install.sh` again to restart it, and edits to `herald.mjs`, `herald-events.mjs`, `herald-notifier.swift` or `sound.mjs` need `queue-board/install-herald.sh`. `sound.json` and `sounds/*.wav` are read fresh each time.
