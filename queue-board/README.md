# The Forge

The Forge is the queue board: a web page that shows what the agent queue is doing on every queue machine. It shows the worker slots (regular and Sentry), each ticket's machine, account, worker state, PR, CI and review state, how long it has run and when it last moved, what needs you, the ready queue, and what merged in the last 48 hours. Everything in it is drawn as Middle-earth, and a herald plays alert cues and posts notifications so you hear about a blocked worker while you work in something else.

The page has seven views, styled after Linear: **Inbox** (your unread Linear notifications), **Sessions** (your Claude app sessions outside the queue, the ones waiting on you first), **Queue** (the worker slots, what needs you, what is building, the ready queue and recent merges), **Middle-earth** (the same workers as animated pixel art, in two drawings: a side view and a map from above), **Machines** (each machine's load, dispatch count, account usage and worktree count, plus Codex and Grok), **Worktrees** (every machine's git worktrees and their state) and **Gollum** (what Gollum is keeping). `#inbox`, `#sessions`, `#scene`, `#map`, `#machines`, `#worktrees` and `#gollum` open those views directly, and `#machines/<host>`, `#worktrees/<host>` or `#gollum/<host>` opens one machine. A bare view name opens at the top of the view: each view's container has the same id as its name, so while the page loaded the browser kept scrolling to it and hid the view's first rows under the header. `atViewTop` in `page.html` puts it back once the page loads or the hash changes.

**The look.** The whole board wears a Middle-earth motif. By day it is parchment and iron-gall ink with a faint paper grain. In dark mode it is Rivendell at night, deep slate with moonlit text and a few stars. Cinzel sets the headings, nav sections and worker names, EB Garamond the titles and messages, and Inter stays for chips, counts and dates so numbers read cleanly. Status marks are cut gems (hollow for not started, half-set while running, whole when done or broken), the inbox is a scroll, the queue a banner and the machines a tower. Each machine shows as its realm, in the nav, the slot groups, the machine cards and the worktree groups, with the machine's own name beside it. Every worker's slot, card and session panel shows its pixel figure from the Middle-earth view (`figureAvatar` and `paintAvatars` in `page.html`, drawn by `sprites.js`). When main is red, an "Orcs at the gates" banner sits over every view with how long, the red commit, the failing jobs and the run, and the herald sounds the war horn (see Sound).

**Realms.** A machine is drawn as one of four realms: Rivendell (elves, teal), the Shire (hobbits, green), Erebor (dwarves, bronze) and Rohan (Men, gold). The realms come from the config key `queueBoard.realms`, a map from host name to `"rivendell"`, `"shire"` or `"erebor"`. With no map, the first three enabled hosts (`dispatcher.enabledHosts`) get Rivendell, the Shire and Erebor in that order. Any further host, and any host with no entry, is a machine of Rohan. The server sends the table to the page in `snap.config.realms`, so the page names no machine.

**More marks.** Each realm has a sigil wherever a machine is named, in the nav, the slot groups, the merged rows, the session chips and the worktree groups: a leaf for Rivendell, a round door for the Shire, a gated mountain for Erebor, a pennant for Rohan and a seeing-stone for Codex and Grok (`sigil()` in `page.html`, drawn as CSS masks on `.mdot[data-r]`). Every count of what waits on you sits in a red wax seal (the sidebar's Inbox, Sessions and Needs you counts, the header's "need you", amber there when it is only worth a look, and the Needs you, Waiting on you and mentions headings), and those rows carry a seal mark, so they share no glyph with Linear's urgent priority. The main panel has a gold diamond at each corner like a map's border, each group heading runs into a double rule from a small gold diamond, and an empty state keeps its plain sentence first, then a short line in the realm's voice ("Nothing needs you right now. All is quiet in the realms."), with a gold leaf before it.

**Laid out for a human glance.** Each view reads the way a person scans it. The Queue opens with Needs you, always in the same place. With nothing waiting it is one calm line, "Nothing needs you right now". Under it every realm is one group in a single band: its name, "1 of 5 at work", a card per busy worker, then one small marker for the free seats and one for an idle Sentry slot, so empty seats cost no room and the whole team fits in one glance. The header stats lead with "needs you", red or amber when it isn't zero. A worker's card has a status line that matches its slot (what is happening now, then what holds the merge: waiting on review, review failed, open threads, never a bare "blocked"), then a PR line. Its machine, account and worker ID sit in the muted facts row, and the dispatcher's note shows only when it says more than the status. Merged rows keep the names in one column so titles line up. The Inbox reads as sentences, who first ("Sam mentioned you on ABC-123 <title>", then their words), with one quiet "Copy for Claude". The title opens Linear. The sound control, Mute and the sound settings, sits at the header's right end.

Open the board at `http://127.0.0.1:<port>` on the machine that runs it (the port is `queueBoard.port`, 8787 by default). Add `"tailscale"` to `queueBoard.bind` and any device on your tailnet can open it by the machine's Tailscale name as well, a phone included once the Tailscale app is on it.

**Install it as an app.** In Chrome on the board's machine, open `http://localhost:8787` and click Install at the right of the address bar (or the menu, Cast, save and share, Install page as app). It opens in its own window, and its Dock icon shows the Needs you count. Chrome installs only from a secure origin. `http://localhost` counts as one. The board's plain-HTTP tailnet names do not (Chrome reports `not-from-secure-origin`), so on other machines and a phone it stays a browser tab. `manifest.webmanifest`, `sw.js` and `icons/` make it installable. The icon is a hammer striking a gold anvil in the forge's glow. `icons/icon.svg` is the tab icon, the sidebar's mark and the source of the PNGs. `icons/maskable.svg` is the same art full-bleed at 80%, for launchers that cut their own shape. `icons/build.sh` renders the four PNGs from the two with `rsvg-convert`, so run it after changing either. The manifest names the app The Forge and colors its title bar like the page. Chrome re-reads the manifest of an installed app on its own schedule and asks before it changes the app's name or icon. To take a new icon at once, remove the app (menu, Uninstall The Forge) and install it again. The service worker serves the page, its scripts and icons from the network first and falls back to its last copy when the board is down, so the app still opens and says it can't reach the board. It never caches `/api`. Browsers that refuse service workers (some built-in ones do) can't test installability, so check it with real Chrome (`Page.getInstallabilityErrors` over DevTools).

## How it works

- `board.mjs` runs on the board's machine (`queueBoard.host`) under launchd (`dev.agent-queue.queue-board`, kept alive; `install.sh` installs it). It listens on the addresses in `queueBoard.bind`, `127.0.0.1` by default, so the LAN can't reach it.
- When the page asks for data and the last snapshot is over 45 seconds old, it builds a new one. With nobody looking and the herald not running there is no work at all.
- A snapshot runs `collect.mjs` on each machine in `dispatcher.enabledHosts` (locally on the board's machine, over SSH on the others, to the destination in `queueBoard.ssh`), then reads the live tickets' PRs from GitHub in one GraphQL call and the queue labels and open asks from Linear in one call.
- `collect.mjs` reads the dispatcher's `state.json`, `PAUSED` and log, `fleet.sh ps`, each account's saved plan usage and the machine's load. It never runs `claude -p /usage`, so it can't crowd the dispatcher's own usage checks. The usage shown is as of the account's last refresh, and the page says how old it is.
- **Outside the queue** lists every other live background worker on the fleet's accounts: one some session started with `fleet.sh dispatch`, such as a rush ticket, with no queue ticket behind it. Nothing has to register it. `collect.mjs` takes every background session in `fleet.sh ps` that has a running process and that no queue ticket ever pointed at. It reads the worker's ticket from its branch or session name, its branch from where it runs (or the newest worktree on that ticket's branch when it started in the workspace folder), its start time from the session registry and its last activity from its transcript. The board then looks up its PR by branch and its title in Linear. The dispatcher counts a working one against its machine's `maxWorkers`, so the slot strip shows it in a slot, marked outside the queue. A finished one drops off a day after its last activity, and a blocked one shows under Needs you. View session and Open in terminal work the same as for a queue worker.
- **Bundles.** One worker and one PR can carry a lead ticket and up to two companions. A companion's state entry names its lead in `bundledInto`, so the board leaves it out of the list and shows it on the lead's entry instead: the slot and the card read "ABC-101 + ABC-102", and the card has a line per companion with its title. A bundle takes one slot, and its companions merge or go stuck with the lead, so they appear on the lead's row under Merged and Needs you too. `#session=<companion>` opens the lead's worker.
- **Queue-low watcher.** `queue-low-watch.mjs` polls the snapshot every 10 minutes and exits with a report when the free worker slots outnumber the ready tickets that wait on no blocker, on two checks in a row (45 minutes at least between reports). Slots held back by account headroom or load are listed apart, since more specs would not fill them. The orchestrator session runs it in the background and specs the next batch when it fires. `--once` prints the current state. `node --test queue-board/queue-low-watch.test.mjs` covers the counting.
- **Merge queue.** A green PR in main's merge queue shows "in merge queue" with its position (GitHub's `mergeQueueEntry`). It is in flight, so the board never flags it as stalled, and neither does `hourly-check.mjs`.
- **Cancelled duplicate checks.** A worker that pushes and then edits its PR seconds later can start two runs of a workflow that cancels its older run, and GitHub keeps both on the commit. The board drops a cancelled run when the same check has another run there, as GitHub's merge check does. Without that, a PR reads "Failing: Ticket ids in the PR title are complete" while its newer run has passed.
- **No daily cap.** Each machine card shows only how many tickets it dispatched in the last 24 hours. The worker slots (`hosts.<name>.maxWorkers`) bound the queue.
- **Sentry slot.** A machine with `hosts.<name>.sentryWorkers` keeps side slots for Sentry fix tickets (label `linear.labels.sentry`), and the board counts them apart from the regular slots. A busy Sentry slot never makes the machine look over-full, and an idle one never shows as a free regular slot. In the slot strip the Sentry bay comes after the machine's regular bays, and the group label reads "<machine> 1/3, Sentry idle" (or busy, or offline). The header shows "Sentry slot idle" next to the building count. A ticket in the slot (`sentry: true` in that machine's `state.json`) carries a Sentry marker on its bay, card and merged row. Each machine card shows its heartbeat age, read from `heartbeats/<host>.json` in `paths.sharedDir`. When a Sentry host's heartbeat is over `sentryHeartbeatMinutes` old (45 by default) or paused, its slot reads offline, its card says Sentry tickets pass to the next machine in line, and Needs you flags it when the machine still ticks. This repo's dispatcher keeps the Sentry slot and takes a pluggable triage module (`sentryTriage` in the config; see the root `README.md` and `dispatcher/README.md`). It ships no triage of its own.
- **The Sentry cascade.** Every machine with `sentryWorkers` has a Sentry slot, and a Sentry ticket goes to the first machine in the order of `dispatcher.enabledHosts` whose heartbeat is fresh, unpaused and says it has Sentry room. `board.mjs` passes each heartbeat's `sentryRoom` and the cascade order (`snap.config.sentryCascade`). Each card's Sentry line says where the machine stands: "idle, first in line", "idle, no room" (amber: busy, low accounts, or the reviewer has the most Sentry reviews waiting), busy or offline. The header counts all of them ("0 of 3 Sentry slots busy"). A Sentry ticket in the ready queue reads "for <realm>'s Sentry slot", naming the machine it goes to now, or "Sentry, waiting for room" when none has room.
- **Swap.** Each machine card has a Swap used row, measured against the machine's RAM (a Mac grows its swap files as it needs them, so its swap total says little). It turns amber at a quarter of RAM and red at half, and the card then names the process holding the most memory, read with `top` on a Mac so compressed pages count. At half of RAM, Needs you flags the machine too. The dispatcher gates on memory free, which can read healthy while a machine pages all day: a machine with 39% free and 14 GB swapped on 24 GB of RAM type-checks at a crawl. `collect.mjs` calls `sysctl` and `top` by full path, since the board's ssh PATH has no `/usr/sbin`. Before that fix every remote Mac's memory read blank.
- **Worker nicknames.** Every live worker has a Middle-earth name, shown ahead of its ticket ID on its slot, its card, its Needs you items, its merged row and the session panel. The board reads `nickname` from each machine's state when the dispatcher gives a ticket one, and names the rest itself. A worker some session started outside the queue has no dispatcher, so `nameWorkers` in `board.mjs` names it from the `adhoc` pool, the wanderers (Gandalf, Radagast, Treebeard and others), and keeps the name in `queue-board-names.json` in `paths.stateDir` while it shows. It also covers a live ticket whose dispatcher has not ticked since it started. The pools live in the config under `queueBoard.nicknames`: a list of names per realm (`rivendell`, `shire`, `erebor`) or per host, plus `sentry`, `adhoc` and `other` (every machine of Rohan). The board reads them at start, so restart it with `queue-board/install.sh` after editing them. Labels that used to say "worker" use the name: the status chip ("Sam is busy", "Thorin failed"), the slot and card status ("Gimli is gone, no PR"), the Needs you text ("Sam is waiting on input in its session"; the "Worker ended" item is now "Ended"), and the session panel's speaker labels and message box. A worker with no name yet reads "the worker".
- **Usage resets.** Under each 5-hour and weekly percentage, for the Claude accounts and for Codex and Grok, the card shows when the window resets as a clock time (with the weekday unless it is today) and a countdown. A reset that has already passed means the reading is from the window before it: the percentage is dimmed and the countdown says how long ago. That is common, since an account's usage is only as fresh as the dispatcher's last `/usage` check on it.

The board changes nothing anywhere and spends no Claude tokens. It uses the same Linear key and GitHub login as the dispatcher. The only things it writes are its own marks (Handled, worker names) in `paths.stateDir`, the sound settings and the herald's status file.

## Session panel

**View session** on a building card or a "Needs you" item opens that worker's session: its recent history and a box to message it.

- **History** comes from `history.mjs`, run on the worker's machine. It reads the session transcript (`<account dir>/projects/*/<session id>.jsonl`) from the end and lists user and worker messages, each tool call with its description and command, failed tool results and error notices. Successful tool output is left out. The panel refreshes every 10 seconds while open, and **Show earlier** reaches back 400 entries.
- **A Codex or Grok worker** has no Claude session, so its panel shows its runs instead. The board shows such a worker when the dispatcher reports one (`driver: 'engine'` in its state entry, with the engine, the round and the engine's name as the account). This repo's dispatcher does not start Codex or Grok workers yet, so with it no such panel appears. The panel reads each round's files from the worker's registry folder on its machine: the brief it was given, the engine's own event stream and its question when it stopped to ask. It gives them in the shape of `history.mjs`: each round opens with its brief, then the engine's messages, each command and file edit, the tail of any failed command, a "Fix round N" marker between rounds, and an open question last. Neither engine's stream carries times, so only a round's start has one. Its card has View session too, and its seat opens the panel. The panel shows no account chip (the mark by its name says what runs it) and no message box, since it reads its brief and takes no messages.
- **Sending** runs `send.py` on the worker's machine. It opens the session with `claude attach` in a pseudo-terminal, pastes the message, presses Enter and disconnects, so the message arrives as your own turn, the same as typing it after `claude attach`. An idle worker reads it at once. A busy one reads it at its next step. A worker blocked on a prompt is refused, since Enter would pick an option there. Answer it with **Open in terminal**. The board log records each send (ticket, worker, length, outcome) but not the text.
- The panel looks the worker up from the dispatcher's own state by ticket ID. The page never names a machine or account. Every route but `/healthz` answers only to this board's own host names (127.0.0.1, localhost, its machine's host name, the addresses in `queueBoard.bind` and its Tailscale names), and sending also needs a JSON body and the `X-Board: send` header, so another website can't trigger it.
- `#session=ABC-123` at the end of the board URL opens that ticket's panel directly.

## Inbox

The Inbox view shows your unread Linear notifications, so a mention or a reply doesn't wait until you ask a session about it. The board's Linear key is your own account, so Linear's `notifications` query returns your inbox. `linear-inbox.mjs` reads it in one GraphQL call (the newest 250 notifications, plus the newest 100 mentions, assignments and review requests so an older mention isn't pushed out), in the background at most every 20 minutes while the page is open. That costs about 1,900 of Linear's 3,000,000 hourly complexity points per read.

- **Mentions, replies and reviews**: someone mentioned you, replied to one of your comments, or asked for your review. The sidebar's Inbox badge counts these.
- **Assigned to you**: issues newly assigned to you.
- **Comments on issues you follow** and **Other updates** (status changes, due dates, PR checks): one row per issue with the newest notice and how many there are. The newest 40 issues of each travel in the snapshot. Linear has the rest.

Each item links to the comment in Linear, and **Copy for Claude** copies the notice and its link to paste into a session. The view only reads: a notice leaves it once you open or archive it in Linear and the next read comes round. Snoozed and archived notices are left out. An inbox can hold hundreds of unread notices, most of them comments on followed issues and status changes, which is why the ones aimed at you come first.

## Sessions

The Sessions view is for the Claude app sessions you run by hand, outside the queue: on a busy day ten or more go back and forth, and the ones that end waiting on you get forgotten. The Claude desktop app keeps a record per Code session in `~/Library/Application Support/Claude/claude-code-sessions/**/local_*.json` and rewrites it as the session works. After each turn it adds a summary: a category (completed, review_ready, blocked), a one-line detail and, when the session needs you, what it needs in its own words (`needs_action`). The record also says when you last opened the session (`lastFocusedAt`), when its last turn ended (`lastTurnEdgeAt`), the session that started it (`spawnedFrom`), the routine that ran it (`scheduledTaskId`) and any error. `sessions.mjs` runs on each machine that has the Claude app and reads the records of the last 14 days that aren't archived. A machine without the app (a Linux box, say) shows no sessions. The script only reads the app's files. Older records are only counted, from a cache of each file's archived flag by modification time (`queue-board-sessions-cache.json` in `paths.stateDir`), so a scan takes about 0.3 seconds once warm. The board runs it in the background at most once a minute while the page is open.

Each session gets one group, in this order:

- **Working now**: a turn under way (activity after its last turn edge, no summary for its latest reply yet).
- **Waiting on you**: its last turn ended needing you, and the row shows what it needs. A session whose last turn never finished and has been silent for 10 minutes joins it as **stopped mid-turn**, most likely on a question or permission prompt in the app.
- **Ready for your review**, **New since you looked** (it did something after you last opened it) and **Errored**.
- **Quiet for 2+ days, never archived** and **Done and seen**, folded: the first holds the ones that get orphaned. The bar at the top counts the older ones never archived.

A routine shows only its latest run. A side session carries a "from <parent>" chip. A dot before the title marks a session that changed since you last opened it. **Handled** hides a row until its session does something new. `board.mjs` keeps the marks in `queue-board-handled.json` in `paths.stateDir` (machine and session, with the activity time they covered), and **Show N marked handled** brings them back. The sidebar's Sessions badge counts the sessions waiting on you that aren't handled. The group says "Waiting on you" so it never reads as the Queue's own "Needs you". **View** opens the session's transcript in the session panel, read-only: the app runs its sessions on the fleet's primary account (`fleet.primaryAccount`), so `history.mjs` reads them as it reads a worker. Replies, archiving and starring happen in the Claude app. The board changes nothing there.

## Worktrees

The Worktrees view lists every git worktree on each queue machine, so a cleanup can see what is safe to remove. `worktrees.mjs` runs on each machine and reads every repo directly under each folder in `queueBoard.repoRoots` (the workspace folder by default). For each linked worktree (the main checkout is left out) it reads the branch, the last commit, how many tracked files have uncommitted changes, how many commits are on no remote branch, and which processes have their working folder inside it (`lsof` on a Mac, `/proc` on Linux). The board then looks up each branch's newest PR on GitHub, one GraphQL call per repository (`worktree-state.mjs`), and gives each worktree one state:

- **In use**: a process is working in it, or a live worker builds its branch.
- **PR open**, **Merged**, **PR closed**: its branch's newest PR.
- **Not pushed**: no PR, and it holds work that is nowhere else.
- **No PR**: no PR, and nothing in it that GitHub lacks.
- **Folder missing**: git still lists it but the folder is gone (`git worktree prune` clears these).

A merged or closed worktree with no uncommitted changes and no commits missing from GitHub counts as **safe to remove**. Commits on no remote branch still count as saved when the worktree's head is the PR's head, which is what a squash merge that deleted the branch leaves behind. Each machine lists the rest first and folds the safe ones into one **Show N safe to remove** line.

The scan runs in the background at most every 10 minutes while the page is open. It only reads: git runs with `--no-optional-locks`, so it never takes the index lock a worker needs, and with `core.preloadIndex=false`, which cut its CPU cost about six times (about 0.1 seconds per worktree). Untracked files are not counted, since finding them cost about four times as much, and `git worktree remove` refuses a worktree that has any. Temporary worktrees in the system temp folders (a jscpd check makes one) are left out.

## Gollum

The Gollum view (`#gollum`) shows what Gollum is keeping, read by `gollum-data.js`'s `grReport()`, the one place his rules live, which both Middle-earth views use too. Gollum's tag on the map once carried all of this and held too much data, so it went and what he reports got a view of its own.

- **The Ring**: every Claude account in the queue that has used 90% or more of its 5-hour or weekly window, the window not yet reset, listed once however many labels and machines hold it (by collect.mjs's key, as on the Accounts card), with each window's use and reset, as the Accounts card words them, and the machines it is signed in on. An account the board only watches does not count.
- **The hoard**: a card per machine, side by side, of its forgotten worktrees, oldest first: a worktree no worker and no process uses, whose last commit is 3 or more days old (7 or more while its PR is open). Each row has the branch, the last commit's age, the PR, the repo when it isn't the main repo, uncommitted changes, commits not on GitHub, and "safe to remove" when the Worktrees view would say so. The folder's path is in its tooltip.
- The nav's Gollum item counts the forgotten worktrees and the accounts past 90%, and is marked while any account is. Clicking a Gollum or his hoard in either Middle-earth view opens his machine's card (`#gollum/<host>`). It only reads (`gollum-view.js`).

## Middle-earth

Eye candy over the Queue's own data: each machine is a realm and each live worker a pixel figure of its people, named by its nickname, acting out where its ticket stands. Rivendell has elves writing at desks by a waterfall in a wooded valley (tall elven trees framing it, a line of smaller ones along the back). The Shire has hobbits hoeing their plots by a hobbit hole with flower beds either side of the round door, wildflowers on the hill and a vegetable patch by the fence. Erebor has dwarves at anvils by the mountain gate and forge. On the road at the edge of the last realm stands a Ranger on horseback by a lantern post, who rides the whole road while the Sentry slot is busy. A busy worker goes on rounds about its realm (below). Workers outside the queue walk the road while busy and stop where they are, asleep, when idle. A machine without a realm gets Rohan. The road along the bottom is 60 rows deep, so the walkers on it have room.

| Ticket state | What the figure does |
|---|---|
| Building | goes on its rounds and works its station (quill, hoe or hammer, with runes, dust or sparks) |
| CI running, worker busy | the same, with an hourglass whenever it stops |
| CI running, worker idle | sleeps at its station (slumped, eyes shut), with an hourglass |
| Idle | sleeps at its station, small "z"s rising |
| CI failing | fights an orc beside its station, under a red "!" (the Ranger: on the road, in mounted charges) |
| Waiting on you (blocked, or an open ask) | raises a hand under an orange "?" |
| Stalled | sleeps under a red "Z", so it reads as a problem |
| Green, merge queue, or waiting on your merge | cheers, a green check |
| Worker ended | a faded ghost, "..." |

**Rounds** (`scene-work.js`). A busy worker doesn't stand at its station: it walks to a spot, works there a few seconds, often carries something back and drops it with an effect, then works its station for a while and picks the next job, each round 15 to 40 seconds. Dwarves chip ore from a rock at the foot of the wall with a pickaxe (chips fly), carry it on the shoulder to the forge and tip it in (the fire flares, sparks fly), and hammer at the anvil. Now and then one kneels at a rock of crystals, digs out a gem, holds it up glinting and carries it to a chest whose pile of gems grows over the session. Hobbits hoe and water their plot, pick vegetables into a basket in the patch, carry it to a cart and tip it in (the cart fills), and stir a kettle of ale by the hill (steam and bubbles). Elves write at the lectern, carry scrolls to and from a rack under the pavilion, shoot three arrows at a straw target (they fly and stick) and go pull them out, play a harp by the falls (notes rise) and gather golden leaves from the trees. Men carry sacks from a pile by the tent to a cart. Each worker's choices and timings come from a generator seeded by its key, so they are stable and no two workers move in step, and a spot holds one worker at a time. A figure walking left is mirrored. The station stays the worker's home and keeps showing how far its PR has come. A worker that stops being busy, or is attacked, drops what it was doing and goes home first. The props (`scenery-props.js`) are placed from each realm's own layout, so they and the spots where workers use them clear the stations, the landmarks and each other at any width, preferring spots clear of the workers at their stations too. A prop with no room is left out, and so is the work that needs it (a narrow Erebor fits one ore rock, a wide one three). The poses, tools and loads are `sprites-work.js`.

**More rounds.** The Shire has a stone well with a crank and bucket, and a pen with two small pigs that wander, root about and lie down. Hobbits wind up a bucket and carry it to water their plot or fill the pigs' trough, and bring the pigs vegetables from the patch or the cart. The pigs come to the trough to eat or drink. Erebor has a treasure vault in the rock, whose hoard grows as dwarves carry gems in from the chest or the gem rock, and an armor stand by a quench trough: a dwarf brings hot metal from the forge, hammers a plate (sparks), quenches it (steam) and hangs it on the stand, which fills and is cleared. Rivendell has a healing house with an herb bed and a mortar, where elves pick and grind herbs. A Rivendell worker that wins a fight walks there to be tended (green sparkles) before going home. Lantern posts line Rivendell's paths, and at sunset an elf walks the round lighting them and at sunrise puts them out (with no elf there they light themselves). Rivendell's trees follow the real season: blossom in spring, green in summer, gold and russet with falling leaves in autumn, frost and a little snow in winter. Deer graze at the valley's edge and bolt while main is red, and birds hop on the tree tops. The new jobs join each people's existing ones through `workAdd` (`scene-jobs.js`), with the same seeded choices and one worker per spot. **Who is calling.** When a sound plays you need to know which worker made it. Each herald event says whose call it is (`who` in `herald-events.mjs`: a ticket's worker, a Claude app session, or a machine, each with a name to show). Before a cue the herald sends those calls with its warning to the board, which passes them at once to every open page on `GET /api/events`. The herald's status file also keeps the last ten minutes of calls, which pages read every 15 seconds with the sound settings, so a page opened after the sound, or a call that rang silent while muted, still shows. In this view (`scene-call.js`) a worker that called stands in a pool of light, with rings of sound going out from its head, and its name glows. A call with no worker in the scene (a machine paused or out of reach, a stuck ticket) sends a messenger of that realm's people onto its road (a session waiting sends a Great Eagle, see below), waving in the same pool of light, with the session's or machine's name. Gold is a call waiting on you, red is trouble (CI failing, stuck, a machine down, main red), green a merge. The bar above the map says what the newest call was and how long ago, with how many more are showing. A call shows for five minutes, or until you click the worker, its name, the messenger or the bar. The bar and a messenger also open what called (the worker's session panel, or the Sessions view). A dismissed call stays dismissed on that device after a reload. With reduced motion the light holds still and no rings go out. Main's own calls and an ask with no worker show only in the bar.

**Orcs.** While a worker's PR has a failing CI check, an orc comes down from the back of its realm and they fight across the open ground near its station (`scene-duel.js`), on the strip between the two rows so they never walk through a landmark or cover another worker's station, and keep inside the realm. A fight runs in exchanges of a few beats: the orc presses in and swings while the worker gives ground and parries (the blades spark), the worker lunges and the orc staggers back, the worker chases it a few steps, they circle and change sides, one hops clear of a swing, and between exchanges they drift back toward the station. Hobbits fight with the hoe and dwarves with the hammer. Elves and Men draw a sword, since a quill doesn't read as a weapon. The Ranger fights its duel on the road, on horseback (below). Once no check is failing (a fix pushed, a re-run started, the PR green or merged), the worker strikes a last blow, the orc falls on its back where it stands and fades while the worker cheers, and the worker walks home. A re-run that fails again brings a new orc. If the worker ends or its ticket leaves the board, the orc fades away. With reduced motion workers stay at their stations and a fight is a still tableau there.

**Only CI brings an orc.** Two things once put orcs on workers whose sessions showed CI running fine. The Claude review's own checks counted as CI: after each push the review check can conclude FAILURE with "Re-review not requested: this head has no review" until a re-review is requested, and that placeholder looked like a failing job. And an orc stayed through the whole re-run after a fix was pushed, so a page left open showed a fight that a freshly opened page did not. Now `shapePr` in `board.mjs` leaves the review's checks (the check named in `github.reviewCheck`, `claude-review-decision`, `claude-review-not-run`, the `claude-review / ` jobs, `request-review`, and any other check that `queueBoard.reviewChecks` matches) out of the snapshot's `ci` lists, so "CI failing", the failing list on a card, the herald's orc drum, the seat's fighting pose and the orcs all mean a CI job failed. The review shows only in the review chip. A review check that failed with one of the review workflow's not-started titles (`queueBoard.reviewNotStartedTitles`, "Re-review not requested", "Review not run" and "CI not green" by default) reads as "review not started" rather than "review failed", and a worker waiting only on the review still looks like it waits on checks. A real review failure, with findings, shows as "review failed" and brings no orc. A ticket already handed to the orchestrator to merge (merge-asked) cheers on the map and raises a hand in its seat, but a failing CI check comes first there too, so it fights. Only a PR in main's merge queue stays green regardless.

**The Sentry's Ranger** (`scene-ride.js`, art in `sprites-horse.js`). Sentry reports bugs, so the Sentry slot's worker is a fighter: a Ranger on horseback who keeps to the road. The horse is about 17 pixels from rump to nose, with a mane and tail, and walks, gallops, grazes and rears. The Ranger is the usual figure seated on it, the horse's barrel drawn over its legs and one boot hanging on the near side.

- **Busy** (building, or checks running while it works): it patrols the whole road at a walk, edge to edge and through every realm's stretch, the way the workers outside the queue walk it: it picks a spot anywhere along the road, rides there, and stops a while, the horse sometimes grazing. Every 10 to 30 seconds (from a generator seeded by its key) a "bug" orc comes onto the road to a place 22 pixels or more ahead of the Ranger (behind it near the end of the road). The orc always comes from its own side of the Ranger, so it never runs through the horse: along the road from the world's end beyond its place when that end is within 80 pixels, or else up from below the road's near verge, off the bottom of the scene. So fights happen all along the road, in every realm's stretch. The Ranger draws its sword and fights it in mounted charges: it gallops in and cuts as it passes, and the orc parries, ducks or takes the hit and staggers. Or the orc swings or lunges and the Ranger parries. It rides on 10 to 15 pixels, wheels round and charges back. The last of two to four passes fells the orc, which falls and fades like a duel's orc, and the Ranger rears with its sword up, then walks back to its patrol. One bug at a time. This is its work routine and isn't tied to any data.
- **CI failing**: the duel's orc comes onto the road the same way, to fight wherever the Ranger is (out on patrol, or by its post if it was at home), and they fight in the same charges, the orc never falling, until no check is failing. The next pass is then the last blow.
- **Main red**: it takes on the nearest free swarm orc anywhere on the road, once that orc is clear of the other riders and their fights, and rides out to it. The orc stops running and fights back, staggering on hits but never falling. It goes free when main is green and the swarm flees. The swarm's hunters never pick the Ranger.
- **Idle, waiting on CI or stalled**: at home by its post, asleep in the saddle while the horse grazes ("z"s rise when idle). **Blocked**: a hand raised high. **Green**: it raises its sword now and then. **Ended**: faded at its post.
- **More than one Ranger**: a realm keeps one post however many Sentry riders it has, and the realm reserves room for that one post only. A second rider, for example one whose ticket is parked on the reviewer's review while the next Sentry fix holds the slot, waits on the road 22 pixels along from the first, so the realm never widens. The sidebar's Sentry count and the "Sentry busy" note leave a parked ticket out, since it holds no slot.
- **Sharing the road**: a patrol heads for spots at least 24 pixels from the other riders (where each is and where each is headed) and 12 from anyone standing still on the road. A bug's or a duel's orc takes its place at least 50 pixels from the other riders and their fights (25 from a still walker), trying a few places and taking the first clear one, and a swarm orc is only taken on once it is that clear, so two riders' charges never cross. Every fight keeps 18 pixels from the world's ends, so each charge has room to ride on and wheel.
- **Home** stays the post in its own realm: idle, waiting, blocked, green or ended, the Ranger rides back to it, at a canter while it is more than 60 pixels away and at a walk for the last stretch.
- With reduced motion it stays at its post, and a duel is a still tableau beside it.

Its name and bubble sit over its head on the horse, and a click anywhere on the horse opens its session.

**Codex and Grok as queue workers.** The board draws Codex and Grok workers as ordinary workers when the dispatcher reports them. This repo's dispatcher does not start such workers yet, so on a stock install none appears. The rules the board follows are these. A dispatcher that ranks Codex and Grok with the Claude accounts hands a ticket to the one with the most weekly usage left. An engine that wins runs the ticket as a full worker with no Claude session behind it: it builds, pushes, opens the PR, then works one round per CI or review fix. Its state ticket carries `driver: 'engine'`, the engine, the round, and the account as the engine's name, and each such worker keeps a registry file on its machine. `collect.mjs` reads those files on each machine and `board.mjs` turns the ticket into a worker (`engine-workers.mjs`): busy, done, blocked (with the worker's question), limit (the engine's plan limit) or failed. The file is read first, since the worker writes it the moment its state changes. The ticket's `engineStatus`, which the dispatcher copies from it once a tick, stands in when the file can't be read. A busy row whose process has died reads as failed once the file is two minutes old, and a ticket the dispatcher's containment audit stopped shows as failed. These workers are named from their machine's own pool and drawn as its own folk, like any worker, because one is just a subagent executing work and needs no different look. Only the engine's mark by the name says what runs it, and from the second round on the round follows the name (`R2`). A blocked one raises a hand, one at its limit sleeps under the red bubble, a failed one fades, as fleet workers do. View session shows its runs (see Session panel). Saruman never sees them: `ext-runs.mjs` counts an `ext-agent.sh` run only when no process above it runs a build worker, and only a wanderer outside the queue named Saruman sends him from the tower. They hold a slot in their machine's pool like any worker and count in "N of M building" against `maxConcurrent`. Each machine has one pool, `hosts.<name>.maxWorkers`, shown as its regular slots in the Queue and the Machines view. There are no engine seats. `collect.mjs` reports which engines the dispatcher may use as `engineAccounts`. The same rule holds for every worker: only a ticket still building holds a slot on its machine, and a PR waiting on the orchestrator's merge or parked on the reviewer's review holds none. Such a worker stays on the board, after the slots with a dashed outline and a note saying what it waits on, and in the Middle-earth views it keeps its station. - **The events.** They keep v1's meanings:

- **Weather and light.** The weather is the real weather of `queueBoard.weather` under the rule that it never covers the work. There are dawn and dusk washes, and night lights.
- **Code.** `scene2.js` (the frame and its hooks: `m2.builds`, `m2.syncs`, `m2.step`, `m2.layers`), `scene2-plan.js` and `scene2-core-places.js` (where everything goes), `scene2-world.js` (the composer), and about a hundred `scene2-*.js` parts named by what they draw. The board serves any `scene2-*.js` without a restart, and `page.html` decides which load.

Everything is drawn in code from rectangles and scaled by a whole number with smoothing off, so there are no image files and every pixel stays square. The map fills the view edge to edge and down to the bottom (`scFit` in `scene.js`): it takes the largest whole-number scale (at least 2) at which the realms fit across, widens every realm by the same share to fill the width, stations centred in the new room, and adds sky above the 190-row scene to fill the height, so the ground and road stay at the bottom and the realm notes stay with their realms. The road along the front is 26 rows deep: grass hanging over its upper edge, a pale shoulder, a far and a near wheel rut that wander a row up or down, tufts of dry grass along the crown between them, stones and dust, and a ragged verge of each realm's own ground along the bottom (`drawRoad` in `scenery.js`). Walkers keep to its middle rows, and riders and their orcs to everything between the shoulder and the verge, which gives a fight's charges room to pass in front of the orc or behind it. The realms carry no titles. A note shows over a realm only when there is something to say: its machine out of reach or paused, or a merge in the last 15 minutes. It sits just above the highest peak (62 rows over the ground, clearing the Lonely Mountain), in the pixel font, pale with a dark shadow at night and dark ink with a light halo by day, following the scene's own clock. The added sky takes its colour from the top of the scene's own sky, red sky and night included, with stars at night and a couple of clouds by day. A resize lays it out again, and so does anything that moves the map's top edge. A phone, too narrow for the realms at scale 2, scrolls the map sideways inside the view. A fallen orc is the same figure turned a quarter turn by an exact canvas transform, so its pixels stay whole. The names and realm notes are HTML over the canvas, so they stay crisp. Names stack instead of overlapping, and a walker's name sits beside it on the road. It animates at about 10 frames a second only while this view is open and the tab is visible. With reduced motion it draws one still frame per snapshot. Workers keep their stations and their fights between snapshots, so nobody jumps when a neighbour finishes. `sprites.js` draws the figures (orcs included), stations and bubbles, `sprites-hd.js` the finer figures, `sprites-work.js` the poses, tools and loads of the rounds and fights, `sprites-horse.js` the Ranger's horse, its riding poses and its post, `scenery.js` the backdrop, the road, the red sky, the fires and the particles, `scenery-props.js` the props and where they go and the Shire's gardens, `scene-work.js` the rounds, `scene-duel.js` how a fight moves, `scene-orcs.js` the duels and the swarm, `scene-ride.js` the mounted Ranger, `scene-tower.js` the dark tower and its Eye, `scene-call.js` who just called (the light, the rings, the messengers and the bar), the files under More rounds the well, pigs, vault, armor stand, healing house, lanterns, seasons and wildlife, `scene-tags.js` the names, the realm notes and the clicks on figures, and `scene.js` lays out the realms and maps each ticket to a mood. The idea comes from [Pixel Agents](https://github.com/pixel-agents-hq/pixel-agents) (MIT): characters at desks that wander when idle, persistent bubbles for "needs you", ghosts for sessions that ended, click to open. No code or art was taken from it. Its characters come from a third-party asset pack.

## Sound

You want to hear it when an agent needs you while you work in something else, so sound is on by default and has a mute for calls. One service plays every alert, so nothing sounds twice and no browser has to be open.

- **The herald** (`herald.mjs`) runs on a Mac under launchd (`dev.agent-queue.queue-herald`, kept alive, installed by `queue-board/install-herald.sh`). Every 20 seconds it reads the board's `/api/snapshot`, works out what changed (`herald-events.mjs`), plays each new event's cue with `afplay` (warning the board 400 ms first, so the music ducks; see Music) and posts a macOS notification titled "Middle-earth" saying who and what ("Frodo is blocked · ABC-123", "Orchestrator session is waiting on you"), with the Forge's icon (see below). Its first read after a start only takes note, so a restart never sounds a burst. A source the snapshot can't speak for (a machine the board never reached, Linear or GitHub failing, sessions not scanned yet) keeps its last state, so its return is no news either. When the board stops answering, the herald keeps trying quietly, posts one notification after 5 minutes, and on the board's return starts from a fresh baseline and says how much waits. Because it reads every 20 seconds, the board refreshes its snapshot about once a minute around the clock while a herald runs. Another Mac can run its own herald against the board's machine (`queue-board/install-herald.sh --base http://<board-machine>:8787`). Its log is `queue-herald.log` in `paths.stateDir`.
- **The notifications carry the Forge's icon.** macOS puts the posting app's icon on a notification, and one sent through `osascript` carries Script Editor's. So the herald posts through its own small app, Forge Herald (`herald-notifier.swift`, about 60 lines of Swift on the UserNotifications API), which `install-herald.sh` compiles into `Forge Herald.app` (in `paths.stateDir`'s `queue-board` folder, or where `queueBoard.heraldNotifierApp` says) with `icons/forge.icns` and signs locally. macOS asks once whether Forge Herald may post. Until it is allowed, on a Mac with no Swift compiler, or whenever the app fails, the herald posts through `osascript` as before and says so once in its log, so no notification is lost. Two things macOS insists on: the first launch has to go through LaunchServices (`open`), or the request is refused with "Notifications are not allowed for this application" and no prompt (the log shows usernoted "Failed to find or validate client"); and closing the prompt without Allow counts as a no, which only System Settings > Notifications > Forge Herald can undo. An AppleScript applet with its own icon was tried first and posts nothing on macOS 26. `forge-herald --status` prints allowed, denied or not-asked.
- **Events and cues**, each its own sound:

| Event | When | Cue |
|---|---|---|
| Needs you | a worker newly blocked on input, a ticket newly carrying an open ask, a PR newly waiting on your merge, or a Claude app session newly waiting on you or stopped mid-turn and not marked handled | a two-tone hand bell |
| Reminder | every 30 minutes (settable) while anything waits on you, with how many and the oldest | three soft taps on a bar |
| Trouble | a ticket newly stuck, a machine out of reach for two snapshots in a row, a machine newly paused | a low tower bell, tolled twice |
| CI failing | a live PR's checks newly failing, when an orc appears in Middle-earth | a short orc drum |
| Merged | a ticket merged, in its realm's voice | Rivendell a harp run, the Shire a whistled jig, Erebor a dwarvish horn call in B-flat |
| Main red | main turns red or gets a new red commit, and every 15 minutes while it stays red | the war horn |
| Main green again | main recovers | a short victory call |

  Several at once play in the table's order with main red first, at most three cues a cycle, and notifications past four fold into one.
- **The cues are code.** `sounds/make.mjs` synthesizes each one with `sounds/dsp.mjs` (struck partials for the bells, a plucked string for the harp, a whistle, and horns) into `sounds/*.wav`: mono 16-bit, matched in loudness, melodies written for this board. `node queue-board/sounds/make.mjs` writes the same files again.
- **Mute and the settings live in one file**, `sound.json` in the `queue-board` folder of `paths.sharedDir` (or where `queueBoard.soundFile` says). The shared folder carries it to every Mac that runs a herald, and the herald reads it every cycle (`sound.mjs` checks every field; a missing file means the defaults). The header's **Mute** toggle (`horn.js`) writes it through `POST /api/sound` (the same X-Board header rule as `/api/send`), so it silences the herald on every Mac while the notifications still post. Muted reads in red with the horn struck through. **Quiet during Zoom**, on by default: while Zoom's meeting process (`CptHost`) runs on the herald's Mac, the herald stays silent and the toggle reads "Muted: Zoom". The button beside Mute opens the settings (`sound-ui.js`): the alert volume, a switch per event (off means no sound and no notification for it), the reminder interval, the music volume, Zoom auto-mute, a Test button per cue that the board plays on its own machine, muted or not, and one line saying whether the herald is running. The herald writes its state every cycle to `herald-status.json` in the same `queue-board` folder under `paths.stateDir` (or where `queueBoard.heraldStatusFile` says), which `GET /api/sound` serves. The settings button turns amber while the herald is stopped or can't read the board.
- **Music.** The header plays your own MP3s as one continuous mix whenever you turn it on. `music.mjs` streams them from the folder in `queueBoard.musicDir` (`~/Music` by default; the `QUEUE_BOARD_MUSIC` environment variable in the board's launchd plist names another folder), one folder per album or flat. The files are yours: the board only reads them, and they are never copied into this repo, the shared folder or anywhere else. `music.mjs` lists every MP3 under that folder at `GET /api/music`, rescanning at most every 5 seconds, so a new album folder joins on its own, and streams one at `GET /music/<id>` with HTTP Range, so seeking works in Chrome and Safari. An id is a hash of the file's path, looked up among the files the scan found, so no path from a request reaches the disk. Links inside the folder are skipped. Titles come from the file names with the disc and track numbers dropped and a stand-in underscore after a title word put back as a colon ("Prologue_ One Ring" reads "Prologue: One Ring"). The player (`music.js`, its CSS in `page.html`) sits just before Mute in every view and keeps playing across views: **Music** plays and pauses, **Next** skips, and while it plays it shows the track, its album and a thin progress line (on a phone, the title only). It shuffles every track, none repeated until all have played, then starts a new order, and fades each track into the next over 4 seconds on two audio elements. **Music volume** in the sound settings is its own, 40 by default, saved in `sound.json` beside the alert volume. Mute, or the herald's quiet for a Zoom meeting, fades it out and pauses it. Unmuting brings it back only if it was playing. The order, the track and its place stay in the browser's localStorage, so a reload carries on (a plain tab waits for the first click or key), and one tab plays at a time: starting it in one stops it in any other. The Mac's media keys play, pause and skip it. The service worker never caches `/music` or `/api/music`.
- **Alerts come before the music.** If the music is playing, the alerts supersede it. Before each cue the herald tells the board it is coming and how long it lasts (`POST /api/alert`, accepted only from the board's own machine with the X-Board header; each cue's length is read once from its WAV header), waits 400 ms and plays it. The settings' Test buttons warn the same way. The board passes the warning at once to every page playing music on an event stream (`GET /api/events`, open only while that page's music is on or its Middle-earth view is open, so other tabs hold no connection). The warning also carries whose calls the cue is for (see Who is calling). The music (`music-duck.js`) fades to silence within 0.3 seconds, before the cue starts, stays silent for the cue's length and a second more, and fades back in over 1.5 seconds. Another alert in that time stretches the silence. The fades run on the audio clock, so the silence always ends by itself, and the stream reconnects by itself after the board restarts. The warning never holds a cue back: a board that is down, slow or broken costs the cue at most those 400 ms.
- **The page plays no alerts.** The page plays only the music you start. The dispatcher's own desktop notifications are off by default so each alert arrives once, from the herald. Its Slack posts are unchanged.
- **Tests.** `node --test queue-board/herald.test.mjs` covers the event rules, reading a cue's length from its WAV header, and the warn-then-play order, including a board that is down, hangs or throws.

## Machines

The Machines view (`machines.js`) is a card per machine dressed as its realm, side by side, then the Accounts card across the grid under them. Every fact a plain card would show is on them, and the numbers stay in Inter.

- **The band** across the top is a pixel diorama (`realm-art.js`): Rivendell's pointed arch between elven trees and a waterfall off a cliff, the Shire's hill with a round door, a round window and a smoking chimney, Erebor's lone mountain with a carved gate and the forge burning inside, and a tent on a golden plain for Rohan. The realm's name is lettered over the sky on the left, and under it the machine's name, whether its dispatcher ticks (or is paused, unreachable or not enabled) and, for a machine with Sentry slots, "4 regular + 1 Sentry". The landmarks keep to the right. It is day in the light theme and night in the dark one, with stars, the lamp in the arch, the lit window and a brighter forge. Like the Middle-earth view it is drawn in code from rectangles, scaled by a whole number (3) with smoothing off, and repainted when the card's width or the theme changes. An unreachable or paused machine's band greys under a mist.
- **Seats**: each worker sits in an arched niche, its pixel figure posed as in the Middle-earth view (cheering when green, a hand raised when it waits on you, fighting while CI fails, at work while busy, asleep while idle, faded once its session ended), with its status gem, its name and its ticket links. Free seats stay visible as dashed niches, and the heading keeps the count ("Workers 5 of 5", or "Regular slots 2 of 4"). The Sentry slot has its own row, busy, idle or offline, and a ticket parked on the reviewer's review sits after it marked "waiting on <reviewer>". Clicking a figure opens its session panel. A ticket ID opens Linear. On a phone the IDs drop their prefix, as the Queue's slots do.
- **The ledger** puts the last tick (with when the next is due), the heartbeat's age and the tickets dispatched in the last 24 hours side by side. **Gauges** for load per core, memory free and swap used are etched: a sunken groove ticked every tenth, filled to the reading, with the limit or floor cut in as a notch.
- Then the worktree line, the machine's own accounts table (5-hour and weekly usage rings with their resets, when the usage was saved, other sessions) and the dispatcher log, which stays open across refreshes. The accounts table is folded behind a toggle, closed by default. Its line names the labels ("Accounts a, b, c, d") and carries a chip when any is signed out or below the floor. Whether each machine's list is open is kept in this browser (`forge.machineAccounts` in localStorage).
- **The Accounts card** (`machines-accounts.js`) spans the grid under the machines and gives one place for every account and the usage it has left. It merges the Codex and Grok card with every Claude account, in three groups (Claude, Codex, Grok), each under a heading with how many of its accounts have room, meaning at least the dispatcher's `headroomFloorPercent` left in both windows. The band's chip and the sidebar's "Accounts" link carry the same count for all of them. Each row has the account, its plan, where it is signed in (each realm links to its card; a Claude row also names the labels it has there, as in "Rivendell (a, d), Erebor (d)"), its 5-hour and weekly use with their resets, and how old the reading is. Under 1100px the plan and the machines fold into the line under the email. A Claude account shows once however many labels and machines hold it: `collect.mjs` gives each account a `key`, the first 12 hex digits of a SHA-256 of its account id and organization id (the ids themselves never leave the machine), rows with the same key are one account with one set of limits, and the row shows the freshest reading. A machine whose `collect.mjs` has no key yet groups by email and plan. The key shows when two labels on a machine are the same seat.
- **A watched Claude account** shows on the Accounts card, first and marked "not in the queue", but never gets queue work. It is a Claude Code folder `~/.claude-board-<name>` on any machine, signed in once by hand with `CLAUDE_CONFIG_DIR=~/.claude-board-main claude auth login --email <address>`. The hyphen in the name keeps it out of the fleet: `fleet.sh` takes only `~/.claude-<letters and digits>` as accounts, so neither `fleet.sh dispatch` nor the dispatcher uses it. `collect.mjs` reads its saved usage like any account's (its `watched` list). `watch-usage.mjs` keeps that fresh: the board runs it every 15 minutes on each machine that has such a folder, and it runs `claude -p /usage`, which asks Anthropic for the windows and runs no model. A refresh that fails puts a "can't refresh" chip on the row with the reason.
- **Frames**, all in CSS with square corners: Rivendell's teal filigree at the four corners over a fine inner line, the Shire's wooden frame pegged with brass, Erebor's riveted iron and a gold rule for Rohan. Codex and Grok are a pair of seeing-stones on plinths, Codex's glowing blue and Grok's amber, the same colours as the small stone beside each of their accounts in the table.

## Codex and Grok

**A signed-out Claude account.** An account's profile file keeps its email after its login is gone, so the board takes sign-outs from the dispatcher's own check (`fleet.sh accounts` each tick, the dispatcher's `signedOut`). Its row on the machine card says how long it has been signed out in place of the last usage it saw, and Needs you says how to sign it back in: account a is that machine's own login (`claude auth login` in a terminal there), any other goes through `fleet/setup/add-account.sh`. The mark clears on the dispatcher's next tick after it signs in.

The Accounts card's Codex and Grok rows show those plans. `ext-usage.mjs` asks each CLI the way its own usage screen does: Codex through `codex app-server` (`account/rateLimits/read`) and Grok through `grok agent stdio` (`_x.ai/billing`, plus `_x.ai/auth/info` for the account email). These are read-only billing calls. Neither starts a session or runs a model, so a reading spends none of the allowance it reports, and the CLIs keep their own sign-in. The board runs it on every machine once an hour, in the background, and merges machines signed in to the same account into one row. The machines can be on different accounts. A machine whose CLI is signed out gets its own row with the error. `queueBoard.extUsage: false` turns it off when you have neither CLI.

## Commands

```
queue-board/install.sh                           # install or restart the launchd job (the board's machine only)
queue-board/install.sh --remove                  # stop it and delete the job
curl -s http://127.0.0.1:8787/api/snapshot | jq  # the raw snapshot
tail <paths.stateDir>/queue-board.log            # its log (~/.agent-queue by default)
queue-board/install-herald.sh                    # install or restart the herald (add --remove to stop it)
tail <paths.stateDir>/queue-herald.log           # the herald's log
node --test queue-board/herald.test.mjs          # the herald's event rules
node queue-board/sounds/make.mjs                 # render the cues again
```

Run the scripts from the checkout that should keep running: the launchd jobs point at the files in the checkout that installed them. Both installers read `agent-queue.config.json` (or the file `AGENT_QUEUE_CONFIG` names) and fill in the plist templates (`queue-board.plist`, `queue-herald.plist`).

`page.html`, the view scripts (every `.js` file in `PAGE_SCRIPTS` in `board.mjs`), `sw.js`, `manifest.webmanifest` and `icons/` are read on every request, so page edits show on reload, in the installed app too. A new view script needs its path added to `PAGE_SCRIPTS` (and `queue-board/install.sh` run again), to `sw.js`'s `SHELL` and to `page.html`'s script tags. A new file under `icons/` needs its path added to `APP_FILES` in `board.mjs`. `collect.mjs`, `history.mjs`, `send.py`, `ext-usage.mjs`, `worktrees.mjs` and `sessions.mjs` run fresh each time on each machine, from the checkout at `queueBoard.remoteRoot` (the same path as the board's checkout by default). Edits to `board.mjs`, `music.mjs`, `linear-inbox.mjs`, `worktree-state.mjs` or `sound.mjs` need `queue-board/install.sh` again to restart it, and edits to `herald.mjs`, `herald-events.mjs`, `herald-notifier.swift` or `sound.mjs` need `queue-board/install-herald.sh`. `sound.json` and `sounds/*.wav` are read fresh each time.
